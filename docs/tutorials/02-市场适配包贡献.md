# 市场适配包贡献：把你手上的芯片接进 elab（作者侧）

> 目标读者：想把自己芯片接入 elab 的社区贡献者。**会写 YAML 就够**，不需要读内核源码。
> 读完你能：建一个独立包仓库 → 用确定性探测把事实填对 → 本地跑通 → 打 topic 自动上架 → 自查被拒原因。
>
> 本篇**不需要硬件**（第 4 章可选上板）。文中所有命令与输出均为本机实跑记录。
> 用户怎么装包见 [插件市场使用](03-插件市场使用_独立WebUI.md)；怎么用包跑闭环见 [芯片开发上手](01-芯片开发上手_独立WebUI.md)。

## 0. 包是数据，不是代码

内核（`services/elab`）**不认识任何厂商**，不为任何芯片开分支。芯片参数、厂商指纹、平台坑位全部住在适配包里：

```
        ┌──────────────────────┐         ┌───────────────────────────┐
        │  elab 内核（骨架）    │  只认    │  适配包（你的仓库）        │
        │  闭环/烧录/串口/OTA  │ ──────► │  pack.yaml                │
        │  不含任何芯片知识    │  协议    │  chips/<chip-id>.yaml     │
        └──────────────────────┘         └───────────────────────────┘
                 ▲                          （数据：参数/指纹/坑位）
                 │  install / activate
            用户本机 packs/installed/<vendor>/<platform>/
```

这个边界是**硬约束**（见仓库根 `AGENTS.md`）：芯片知识写进 `services/elab/**` 或 `cockpit/**` 属于分层违规；外置包也不得放进本仓 `packs/official/**`。

一句话原则：**适配包是数据，不是代码**——包内只有 YAML、说明文档和可审阅的 C 源码（由用户自己的工具链现场编译）。

## 1. 市场链路一张图

零服务器：市场 = **一份 `index.json`** + **作者仓库里的包内容**。没有注册中心、没有数据库、没有人工审核。

```
  你的 GitHub 仓库                     市场仓 xkk6663/elab-pack-market            用户
  ┌────────────────────┐   打 topic    ┌──────────────────────────────┐   读索引   ┌──────────────┐
  │ elab-pack-acme-…   │ ──elab-pack──►│ Actions 每小时（cron）        │ ─────────► │ pkg search   │
  │  pack.yaml         │               │  1 GitHub 搜索发现            │            │ pkg install  │
  │  chips/*.yaml      │               │  2 clone 到固定 ref           │            │ （按名安装） │
  │  .gitattributes    │               │  3 机器校验（schema/安全/握手）│            └──────┬───────┘
  └────────────────────┘               │  4 机器人重算 tree_hash       │                   │
                                       │  5 写入 index.json（变化才提交）│                   ▼
                                       │  报告：report.json            │          强校验 sha256 后
                                       └──────────────────────────────┘          落到 packs/installed/
```

关键性质：

- **上架 = 机器校验通过**。不合格仓库只是被跳过，原因写进 `report.json`，不影响别人；
- **作者不需要提供 sha256**，也提供不了（机器人亲自用 `tree_hash` 算，安装时内核再强校验一次）；
- **没有 PR / 评审 / 合并环节**，你唯一要做的动作是「推代码 + 打 topic」。

## 2. 建仓骨架

### 2.1 目录结构

```
elab-pack-acme-acme32/            # 独立仓库（不得放进 elab-Flow 的 packs/official/**）
├── .gitattributes                # 必须：* -text   ← 缺少它 = 别人安装必失败
├── LICENSE                       # 必须与 pack.yaml 的 license 一致
├── README.md                     # 支持哪些芯片、来源、已知坑位、验证到什么程度
├── pack.yaml                     # 包清单（schema_version: 1）
└── chips/
    ├── acme32x.yaml              # 一颗芯片一份
    └── ...
```

### 2.2 `pack.yaml`（清单）

```yaml
schema_version: 1
name: acme/acme32            # vendor/platform；小写 [a-z0-9._-]；全局唯一
vendor: acme
platform: acme32
version: 0.1.0               # 语义化；改包内容必须升
license: MIT
status: community            # 社区包恒为 community（official 仅本仓维护者）
description: ACME32 芯片适配包（工程指纹 + 芯片参数 + 平台坑位）

requires:                    # 兼容性握手；不满足时安装 fail-fast
  kernel_api: ">=1 <2"
  schema_version: 1

vendor_fingerprints:         # 供 `elab adapt` 确定性探测（可选，但强烈建议）
  - generator: acme_workbench
    gen_dir: acme_workbench     # 工程里 add_subdirectory(cmake/<gen_dir>) 的目录名
    syms_var: ACME_Defines_Syms # 该目录 CMakeLists.txt 里的编译宏变量名
    project_glob: "*.ACWP"      # 生成器工程文件（辅助证据，可能过期）
```

字段含义直接对应探测器的三类证据：`gen_dir` → `E4` 厂商证据、`syms_var` → `E1` 芯片宏证据、`project_glob` → `E5` 辅助证据。

### 2.3 `chips/<chip-id>.yaml`（芯片参数）

最小可用只要 `id / vendor / platform / part / core / memory`；建议同时给出 `debug`（openocd target / svd / device）、`verify`（doctor 漂移校验的期望值）与 `pitfalls`（你踩过的坑，会进入平台 skill）。

```yaml
id: acme32x
vendor: acme
family: acme32
platform: acme32             # 同一 platform 的芯片聚合生成一份平台 skill
part: ACME32X                # 实测编译宏
core:
  arch: arm
  cpu: cortex-m4
  fpu: hard                  # hard → -mfloat-abi=hard；soft → 不生成 -mfpu
memory:
  flash: { origin: 0x08000000, length: 0x20000 }
  ram:   { origin: 0x20000000, length: 0x8000 }
debug:
  openocd_target: target/acme32x.cfg
  device: ACME32X
verify:
  expect_defines: [ACME32X]
  expect_flags:   ["-mcpu=cortex-m4", "-mfloat-abi=hard"]
  expect_memory:  { flash: 0x20000, ram: 0x8000 }
pitfalls:
  - "一句话写清楚你踩过的坑和修法。"
```

> 完整字段与真实取值以本仓 `packs/official/st/stm32/chips/stm32f411ceux.yaml`（含 OTA 分区表）与社区包 `packs/installed/artery/at32/chips/at32f421g8.yaml`（含软浮点、双重链接参数坑）为模板。**只写数据，不写脚本。**

### 2.4 `.gitattributes`（必须）

```
* -text
```

内容哈希按**字节**计算。Windows/macOS 的换行转换会让 `sha256` 对不上：你本机 `verify` 通过、别人 `install` 失败，而且报错看起来像"哈希被篡改"。

## 3. 用探测把事实填对

**不要手抄寄存器表**。`elab adapt --probe` 对你给的厂商工程做确定性探测，逐条列出证据链，你照着填 `chips/*.yaml` 即可。本机实跑（对 `examples/STM32F411CEU6`）：

```text
$ elab.cmd adapt examples/STM32F411CEU6 --probe
[adapt] 目标：C:/Users/xiao1/Desktop/ELAB/dsh-elab-flow/examples/STM32F411CEU6
  档位      : T1
  厂商/生成器: st / stm32cubemx
  形态      : A 类
  芯片      : st/stm32f411ceux   [宏 STM32F411xE]
  工程名    : 411   → 产物 411.elf/hex/bin/map
  链接脚本  : STM32F411XX_FLASH.ld   (链接变量 CMAKE_EXE_LINKER_FLAGS)
  编译参数  : -mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard
  内存      : RAM=0x20000 FLASH=0x80000
  输出能力  : 有 → 将生成 monitor 判据，串口闭环可被机器判定

  证据链：
    [E1] project_name    CMakeLists.txt: set(CMAKE_PROJECT_NAME 411)
    [E1] compile_flags   工具链文件: TARGET_FLAGS
    [E1] chip_macro      cmake/stm32cubemx/CMakeLists.txt: MX_Defines_Syms → USE_HAL_DRIVER, STM32F411xE
    [E1] chip            编译宏 STM32F411xE == 适配包芯片 st/stm32f411ceux:part
    [E3] linker_script   工具链文件: -T STM32F411XX_FLASH.ld
    [E3] memory          STM32F411XX_FLASH.ld MEMORY 段
    [E4] vendor          CMakeLists.txt: add_subdirectory(cmake/stm32cubemx)
    [E4] archetype       CMakePresets.json: toolchainFile（命令行级，接管后不再加载）
    [E4] toolchain_cmake CMakePresets.json: toolchainFile = cmake/gcc-arm-none-eabi.cmake
    [E4] uses_freertos   cmake/stm32cubemx/CMakeLists.txt: add_library(FreeRTOS OBJECT)
    [E4] stdout          Core/Src/freertos.c: 定义了 __io_putchar（带函数体）；Core/Src/freertos.c: 调用了 printf

  · 提示（已解决/仅供参考，不阻断）：
    - cmake/ 下另有候选工具链 ['cmake/starm-clang.cmake']，已按 CMakePresets.json 指定的 cmake/gcc-arm-none-eabi.cmake 为准（其余不参与）

  置信度：high
```

怎么读这份报告：

| 证据 | 你该填哪儿 |
|---|---|
| `[E1] chip_macro` | `part`（族级宏，不是封装型号）与 `compiler_defines` |
| `[E1] compile_flags` | `core.cpu / fpu / mfpu`，以及 `verify.expect_flags` |
| `[E3] memory` | `memory.flash / ram` 与 `verify.expect_memory` |
| `[E3] linker_script` | `linker.filename`（ld 归工程所有时只记名字） |
| `[E4] vendor` + `gen_dir` | `vendor_fingerprints`（决定 `adapt` 能不能认出你的工程） |
| `[E4] toolchain_cmake` / `archetype` | 写进 `pitfalls`：A 类（preset 带工具链）与 B 类（`include` 硬挂）坑位不同 |
| `输出能力` | 有输出 → 会生成 monitor 判据，串口闭环可判 |

**重要**：`--probe` 是只读，默认行为；只有加 `--write` 才会生成 `projects/<name>.yaml`（那是**用户侧**接入，不是包的产出）。

> 探测结论分三档：T1 直接可适配 / T2 需少量人工补齐 / T3 需人工介入。你的包若让同类工程落到 T3，先检查 `vendor_fingerprints` 是否写准。

## 4. 本地先跑通，再上架

四步，顺序不能换（每一步都在给下一步减少不确定性）：

```text
① adapt --probe      看清事实（只读）
② pkg install --from 装本地包（跳过哈希，便于迭代）
③ pkg verify         结构/安全/哈希 —— 这就是上架时的机器校验
④ doctor / build     真跑一遍闭环（有探针再加三连）
```

### 4.1 装本地包

```powershell
elab.cmd pkg install ./my-pack --from ./my-pack
```

`--from` 表示"源目录"，本地自测**不校验哈希**（因为包还在你手里改）。

### 4.2 校验（上架同款判定）

本机实跑：

```text
$ elab.cmd pkg verify
  [✓] artery/at32  C:/Users/xiao1/Desktop/ELAB/dsh-elab-flow/packs/installed/artery/at32
  [✓] st/stm32  C:/Users/xiao1/Desktop/ELAB/dsh-elab-flow/packs/installed/st/stm32
```

`verify` 通过的判定：**结构合法 + 无禁用文件 + `tree_hash` 与 `.installed.json` 一致**。这一步用的就是市场仓机器人那套逻辑——本地全绿，上架基本不会因格式被拒。

### 4.3 看已装与启用标记

```text
$ elab.cmd pkg list
[elab] 安装目录：…/packs/installed
[elab] 搜索根：…/packs/installed, …/packs/official
  已装 　　 artery/at32        v0.1.0   [community] …/packs/installed/artery/at32
       chips：artery/at32f421g8
  已装 启用 st/stm32           v0.1.0   [official] …/packs/installed/st/stm32
       chips：st/stm32f103xb, st/stm32f411ceux
```

注意两行的差别：`启用` 标记只出现在当前生效的那套（`packs/installed/active.json` 决定）。一次只启用一套，其余照常留在本地。

### 4.4 真跑闭环

```powershell
elab.cmd pkg activate acme/acme32                    # 启用你的包（自动重生成平台 skill）
elab.cmd doctor -p <project> --deep
elab.cmd build  -p <project>
elab.cmd run    -p <project> --steps build,flash,debug_verify   # 三连：有探针时
elab.cmd loop   -p <project>                                    # 完整闭环（含体检与串口判据）
```

本机实跑 `doctor` 的结论（节选）：

```text
  [OK  ] chip.stm32f411ceux.cpu cortex-m4
  [info] chip.stm32f411ceux.fpu hard → -mfloat-abi=hard
  [OK  ] chip.stm32f411ceux.target target/stm32f4x.cfg
  [OK  ] drift.f411.ota-layout  ota_layout ↔ 烧录地址 ↔ ld 三方一致（2 镜像）
  [OK  ] drift.f411.memory      双镜像布局合法（2 镜像 ⊆ 芯片物理，flash 分区互斥）
  [OK  ] convention.f411.elf    通用工具链带 .elf 后缀约定 (C5)

[elab] ✓ 体检通过
```

`doctor` 是**双源漂移校验**：拿你 `chips/*.yaml` 里的 `verify.expect_*` 去比对工程实际编译参数。它绿了，说明"包里的数据"和"工程里的事实"没有分叉——这正是适配包的主要价值：**一份可校验的单一真相**。

**常见坑**：Windows 下 `elab.cmd` 包装脚本会先打印两行乱码（`'命令行入口（Windows' is not recognized…`），那是批处理文件的编码问题，不影响命令本身执行，看后面的 `[elab]` 输出即可。

## 5. 上架

1. 推到**独立 GitHub 仓库**，建议命名 `elab-pack-<vendor>-<platform>`；
2. 确认仓库根有 `.gitattributes`（内容 `* -text`）；
3. 仓库首页 → About 右侧 ⚙ → **Topics** → 输入 `elab-pack` 保存（topic 是正式上架标记；仓库名含 `elab-pack` 也会被搜到，但建议两样都有）；
4. （可选但推荐）打语义化 tag `v0.1.0`。

然后不用再做什么。市场仓 Actions 每小时自动执行：

```
GitHub 搜索发现（topic + 仓库名两条查询合并去重）
  → 逐仓 clone 到固定 ref（最高 semver tag；无 tag 用默认分支 commit SHA）
  → 机器校验（schema / requires 握手 / 安全审计 / .gitattributes）
  → 机器人用 tree_hash 重算 sha256
  → 写入 index.json（有变化才提交，bot 身份）
```

索引条目形如（机器生成，仅供排查）：

```json
{
  "name": "acme/acme32",
  "version": "0.1.0",
  "status": "community",
  "license": "MIT",
  "requires": { "kernel_api": ">=1 <2", "schema_version": 1 },
  "chips": ["acme/acme32x"],
  "source": { "type": "git", "url": "https://github.com/<you>/elab-pack-acme-acme32.git", "ref": "v0.1.0" },
  "sha256": "<机器人计算>"
}
```

`ref` 固定到 tag 或 commit SHA → 用户装到的是**可复现的那一份**，不会因为作者 force-push 而悄悄换内容。

**上架后怎么确认**：用户侧 `elab.cmd pkg search acme` 能搜到，或看市场仓 Actions 的 `report.json`。

## 6. 机器准入 7 条

| # | 检查 | 不通过的结果 |
|---|---|---|
| 1 | `pack.yaml`：`schema_version=1`、必填字段齐全、`name = vendor/platform` 一致、semver 版本 | 跳过该仓库 |
| 2 | `requires.kernel_api` / `schema_version` 与当前内核握手 | 跳过（注明要求的区间） |
| 3 | 安全审计：无脚本 / 无预编译二进制 / 无符号链接（`pkg.audit_dir`） | 跳过并列出命中文件 |
| 4 | 至少一颗 `chips/**/*.yaml`，且芯片 `vendor` 与包一致 | 跳过 |
| 5 | `.gitattributes` 含 `* -text` | 跳过 |
| 6 | 内容哈希由机器人用 `pkg.tree_hash` 重算（作者自报值一律忽略） | —（不会拒绝，只会覆盖你的数字） |
| 7 | 同名包只保留版本最高者 | 被取代者不上架 |

禁止文件类型（第 3 条的具体名单）：`.exe .dll .so .a .lib .o .bin .hex .elf .py .js .ts .sh .bat .ps1 …`。
**C 源码（`.c/.h`）允许**——它是可审阅源码，由用户工具链现场编译。

每条判定结果都写在市场仓 Actions 的 `report.json` 产物里：**规则公开、结果可查**，这正是"无人工审核"能成立的前提。

## 7. 版本、下架与封禁

| 动作 | 要求 |
|---|---|
| 改芯片参数 / 指纹 / 坑位 | 升 `version`（建议打新 tag；`sha256` 由机器人重算） |
| 只改 README | 不必升版本（索引不记 README） |
| 修安全 / 兼容问题 | 升版本，并在 README / Release 说明影响面（哪些芯片受影响） |
| 下架 | 删掉仓库的 `elab-pack` topic（或归档仓库），下一轮自动移除；已装用户本地副本不受影响（`elab pkg remove <name>`） |
| 紧急封禁 | 恶性包由维护者在索引仓 `blocklist.json` 加一行仓库地址（非常规流程） |
| 同版本重装 | 需 `--force`（面板上是「更新」按钮） |

**不升版本的后果**：用户 `update` 按索引里的旧哈希校验新内容 → 「内容哈希漂移」安装失败。这是最常见、也最容易自查的一类问题。

## 8. 常见被拒与自查

| 症状 | 原因 | 修法 |
|---|---|---|
| 本机 `verify` 过，别人 `install` 报哈希漂移 | `.gitattributes` 缺失，换行被转换 | 加 `* -text`，重新提交并升版本 |
| `pkg search` 搜不到 | 没打 `elab-pack` topic；或索引每小时才刷新（远程索引另有 5 分钟内存缓存） | 补 topic，等一轮 |
| 上架被跳过，report 说 schema 不合法 | `schema_version` 缺失 / `name` 与 `vendor/platform` 不一致 / 版本不是 `x.y.z` | 按 §2.2 对齐 |
| 上架被跳过：安全审计命中 | 包里有 `.py/.sh/.bin` 等禁用文件 | 删掉；需要生成物就让用户工具链现场编译 |
| 上架被跳过：requires 不兼容 | `kernel_api` 区间没覆盖当前内核 | 改诚实区间；不要用 `>=1` 蒙混 |
| 上架被跳过：没有 `chips/*.yaml` | 只写了 `pack.yaml` | 至少补一颗芯片 |
| 同厂商两个包装上反而都不生效 | 拆成了"必须同时装"的多包 | 合并成一个 `vendor/platform` 包（一次只启用一套） |
| 安装按钮置灰 | `requires` 内核版本高于用户机器 | 用户升级内核，或你下调要求并真实验证 |
| 被取代（同名只留最高版本） | 同名包有更高版本 | 正常行为；升你自己的版本号即可 |
| 想同时保留多套包 | — | 直接装多套，`elab pkg activate <name>` 切换，本地可存很多套 |

**排查入口**：市场仓 Actions 运行记录的 `report.json` —— 谁被拒、为什么被拒都在里面。本地等价命令：

```powershell
elab.cmd pkg index --remote --out index.json --report report.json   # 本机跑同一套逻辑
```

## 附录：官方包怎么写

官方包 `packs/official/st/stm32` 遵守与社区包**完全相同**的格式规则——它对格式是最好的自吃狗粮。

改动官方包后必须重生成索引，CI 会拦漂移：

```powershell
elab.cmd pkg index           # 重生成 market/index.json
elab.cmd pkg index --check   # 只校验（CI 同款）——本机实跑：✓ 市场索引与包内容一致
```

要点：

- 改 `packs/official/**` 的**任何字节**（含换行）都会变 `sha256` → 必须重跑 `pkg index`；
- 外置条目（`git`/`archive`）由作者仓库负责，不参与本仓 `--check` 比对；
- 官方包**不进**自动市场索引（随骨架离线分发），所以市场里不会出现 `status: official` 的条目；
- 新增外置厂商包必须是独立仓库，不能塞进 `packs/official/**`；
- `packs/installed/` 是用户安装落点，**不入库**。
