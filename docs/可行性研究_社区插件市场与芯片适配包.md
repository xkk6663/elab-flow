# 可行性研究：社区插件市场与芯片适配包

> 状态：调研结论（2026-10-31）。回答一个问题：**能否把"芯片适配"从本仓拆成社区可维护、市场可分发的适配包，本仓只保留通用嵌入式开发骨架？**
> 结论先行：**可行，且本仓已完成约 80% 的前置条件**——适配在本仓已经是纯数据形态（YAML + 生成器），缺的只是"发现 → 获取 → 落盘 → 校验"这条分发链路。推荐按 **Git 索引市场 + `elab pkg` CLI** 起步，零服务器成本。

---

## 1. 目标形态与对标原则

### 1.1 用户理想中的开发形态

```
① 下载通用工具（elab 骨架 + DSH 驾驶舱面板，不含任何具体芯片）
② 在社区市场拉取自己芯片的适配包（如 st/stm32f411、artery/at32f421、gd32/…）
③ 按需取用：elab adapt 接入自己的工程 → doctor 校验 → build/flash/debug/monitor 闭环
```

官方（我们）只维护 st、artery 等已适配家族作为**官方包**；其余芯片由社区贡献适配包。

### 1.2 deepseek-harness 的"一切皆插件"（对标物）

[deepseek-harness（dsh）](https://github.com/deepseek-ai/deepseek-harness) 是 DeepSeek 开源的 agent harness，MIT 协议，基于 Cordis 框架的
"everything is a plugin" 架构：模型、工具、会话、沙箱全部是插件。对本方案最有参考价值的一点：

- **dsh 自己也没有中心化市场服务端**——插件发现走 GitHub topic `dsh-plugin`（仓库给自己打上
  topic 即可被发现），开发预览期明示会有破坏性变更。
- 启示：**"插件市场"的最低可行形态 = 约定清单格式 + Git 索引 + CLI**，不需要先建服务端。

### 1.3 原则映射

| dsh 中的做法 | 本仓的对应物 |
|---|---|
| 一切运行时能力皆插件 | 一切**芯片差异**皆数据包（chips YAML + 可选 C 端口） |
| Cordis 提供骨架 | elab 内核 + DSH 面板提供通用骨架（编译/烧录/调试/串口闭环） |
| GitHub topic `dsh-plugin` 发现 | `elab pkg search` 读市场索引仓（可叠加 topic `elab-pack` 辅助发现） |
| 插件不侵入宿主 | 适配包不侵入内核：分层规则（AGENTS.md）天然保障，包落在业务层 |

## 2. 现状盘点：本仓"适配一颗芯片"的解剖

这是可行性的根基：**适配在本仓已高度数据化，内核几乎零 per-chip 分支。**

### 2.1 适配的文件构成（现状，全部有实证）

| 层 | 文件 | 性质 | 属于"芯片适配包"吗 |
|---|---|---|---|
| L1 芯片参数 | `chips/<vendor>/<chip>.yaml`（如 `chips/artery/at32f421g8.yaml`） | **纯数据**，注释明言"芯片差异的唯一数据载体……不侵入任何业务代码"（`chips/artery/at32f421g8.yaml:1-2`） | ✅ 必需，包的核心 |
| L4 工程接入 | `projects/<name>.yaml` | **纯数据**，由 `elab adapt` 确定性生成，带 E1–E6 证据链与 provenance | ➖ 属于"用户工程接入"，不由市场分发（模板可随包提供） |
| L6 AI skill | `skills/<vendor>/<platform>/SKILL.md`（镜像到 `.agents/skills/<platform>/`） | **生成物**：`elab skill`（`services/elab/skillgen.py:231,240`）从 chips/projects YAML 渲染，禁止手改 | ❌ 不进包，**安装后本地重生成** |
| 板级示例 | `examples/<board>/`（含厂商 SDK） | 用户工程 + 厂商库 | ➖ 模板可选随包，SDK 有版权约束（见 §7.4） |
| 组件端口 | `components/ota/port/<chip>/`、`components/serial/port/<chip>/` | C 源码，仅当工程用 OTA/serial 组件才需要 | ✅ 可选（C 源码，用户工具链现场编译） |
| L0 主机事实 | `elab.host.yaml`（工具链路径、探针、svd_roots） | 纯数据，但属于**用户主机** | ❌ 不进包（包只声明"需要什么"，doctor 引导用户配 host） |
| 跨芯片公共层 | `toolchains/gcc.cmake`、`inject.cmake`、`gdb/break_main.gdb` | 通用骨架 | ❌ 骨架的一部分，随内核仓分发 |
| 内核步骤 | `cockpit/server.py` 的 `STEP_META` / `KERNEL_PLANS`（`cockpit/server.py:62-78`） | **芯片无关**的全局自描述 | ❌ 骨架 |
| 工具层兜底 | `packages/dsh-elab-cockpit/lib/domain/kernel-meta.js` | 只消费内核 meta，过期才兜底，**零芯片知识** | ❌ 骨架 |

### 2.2 内核的数据驱动程度（关键评估）

- 内核各步骤（build/flash/debug/monitor）全部从 `chips/*.yaml` + `projects/*.yaml` 读数据驱动；
  全内核唯一的 per-vendor 代码是 `services/elab/adapt.py:50-52` 的**厂商指纹表**
  （`VENDOR_BY_GEN_DIR = {"at32_workbench": "artery", "stm32cubemx": "st"}`）。
  这不是业务分支，而是"适配探测器"的注册表——**本身就应该数据化**（见 §5.4）。
- 结论：**新芯片适配 ≈ 新增数据文件 + 可选 C 端口，零内核/工具层改动。**
  这正是"适配包可以外包给社区"的结构性前提。

### 2.3 适配流程已经产品化（社区贡献者的现成入口）

```
elab adapt <厂商工程> --write   # 确定性探测生成 projects/*.yaml（证据分级 E1–E6，不猜）
elab skill                      # 由 chips/*.yaml 重新生成平台 skill
elab doctor [--deep]            # 两源漂移校验（chip.yaml 期望值 vs 工程实际编译参数）
elab ci                         # 按 ci/matrix.yaml 跑门禁
```

`ci/matrix.yaml` 的 `host-gate` 档（doctor_deep + 全芯片编译）**云端 runner 可跑**，
`onhw-gate`（烧录/调试）走 self-hosted——这套门禁可直接复用为市场包的 CI 准入（见 §6）。

### 2.4 版本握手已存在

工具层已通过 `capabilities.meta`（`STEP_META`/`KERNEL_PLANS`/`COCKPIT_VERSION`）与内核做
版本握手（§16 分层解耦已落地）。适配包的 `requires` 字段可以挂进同一握手体系，安装时校验
内核兼容性，而不是"装上之后跑到一半才发现不匹配"。

## 3. 业界调研：插件市场/包仓库形态

调研了六个最相关的生态，提炼出市场四要素：**清单（manifest）、索引（index）、分发通道
（transport）、信任（trust）**。

| 生态 | 清单 | 索引 | 分发 | 审核/信任 | 服务器成本 |
|---|---|---|---|---|---|
| [PlatformIO Registry](https://docs.platformio.org/en/latest/platforms/creating_platform.html) | `platform.json`（声明 toolchain/SDK/flasher 等依赖，每个都是 `owner/name` 包） | 中心化 registry | 中心 registry 二进制包，缓存到 `~/.platformio`；6.0 起支持本地目录/URL/私服 | 官方+社区共注册表，厂商可自营 platform | 高（自建服务端） |
| [ESP-IDF Component Registry](https://docs.espressif.com/projects/idf-component-manager/en/latest/reference/manifest_file.html) | `idf_component.yml`（组件根目录，声明依赖版本约束） | [components.espressif.com](https://components.espressif.com/) 中心枢纽 | CMake 运行时自动解析依赖到 `managed_components/`；支持私有 registry | 官方注册表 + 版本约束（`^9.1.0`） | 高 |
| [CMSIS-Pack / Open-CMSIS](https://open-cmsis-pack.github.io/Open-CMSIS-Pack-Spec/main/html/createPackPublish.html)（嵌入式芯片支持包的行业标准，ST/Artery 都在发） | `.pdsc`（XML，描述器件/组件/Flash 算法） | 厂商各自维护 `<vendor>.pidx`，Arm 聚合成 [keil.com/pack/index.pidx](https://www.keil.arm.com/pack) | `.pack`（zip）托管在任意公开 URL；`cpackget` 安装 | `packChk` 校验 + 厂商索引聚合（联邦式） | 低（索引聚合，内容任意托管） |
| [Obsidian 社区插件](https://github.com/obsidianmd/obsidian-releases) | 插件仓库内 `manifest.json` | GitHub 仓库里一份 `community-plugins.json`（**目录，不托管代码**） | 代码走作者自己的 GitHub Release（tag 必须等于 manifest 版本） | PR 提交 + 官方审核后进入目录；下载量经 GitHub API 统计 | **≈0**（纯 GitHub） |
| [VS Code Marketplace / OpenVSX](https://open-vsx.org) | `package.json` + `.vsix` | 中心化（微软闭源 / Eclipse 开放镜像） | 中心市场 | 中心审核；2025 年 VS Code 市场遭 Shai-Hulud 供应链蠕虫，暴露可执行插件市场的审核风险 | 高 |
| Homebrew tap / npm | formula / `package.json` | **git 仓库即索引**（tap）；npm 中心 registry | git + bottle / registry | 轻审核；npm 生态有 cosign/provenance 等签名方案 | tap ≈0 |

**提炼：**

1. **两条路线**：中心化 registry（PlatformIO/ESP-IDF/OpenVSX——体验最好，但要养服务端和审核团队）
   vs **Git 索引联邦式**（CMSIS-Pack 的 pidx 聚合、Obsidian 的目录仓、Homebrew tap——零服务器，
   代码留在作者仓库，信任靠"索引准入审核 + 内容哈希"）。
2. **与我们最像的是 CMSIS-Pack**（同为"芯片支持包"），**最可抄的是 Obsidian 模式**（零成本起步，
   PR 即上架，GitHub Release 即分发）。dsh 自己也处于"GitHub topic 发现"的零服务端阶段。
3. **可执行插件市场（VS Code）出过真实供应链事故**；我们的适配包默认是数据 + C 源码、
   **无脚本执行面**，风险面天然小一档（见 §7.1）。

## 4. 方案设计（推荐形态）

### 4.1 总体形态

```
┌────────────────────────────────────────────────────────────┐
│ elab 内核仓（本仓瘦身版）                                    │
│   services/elab + cockpit + toolchains/ + 通用 components   │
│   + 内置官方包（st、artery 随仓分发，离线可用）                │
├────────────────────────────────────────────────────────────┤
│ 市场索引仓（新，GitHub：elab-market）                        │
│   market.json  ← PR 上架，CI 校验                            │
│   每条 = {name, vendor, version, source, sha256,            │
│           requires, status: official|community, license}    │
├────────────────────────────────────────────────────────────┤
│ 适配包仓库（每包一仓，或 monorepo 子目录 → tag 发布）          │
│   st/stm32f4 · st/stm32f1 · artery/at32f421 · gd32/… (社区) │
│   pack.yaml + chips/ + ports/ + templates/                  │
└────────────────────────────────────────────────────────────┘
用户侧：elab pkg install artery/at32f421 → 落盘 packs/ → skill 重生成 → doctor
```

### 4.2 适配包格式（elab-pack）草案

```
<pack-root>/                        # 仓库根（或 monorepo 子目录）
├── pack.yaml                       # ★ 包清单（见下）
├── chips/
│   └── at32f421g8.yaml             # 与本仓现有 chips/ 格式完全一致（§2.1）
├── ports/                          # 可选：组件 C 端口（仅 OTA/serial 等用到时）
│   └── at32/ota_*.c|.h             # 安装时映射到 components/*/port/<platform>/
└── templates/                      # 可选：工程接入模板 / 最小示例（不含厂商 SDK）
    └── README.md
```

`pack.yaml` 清单（schema 草案）：

```yaml
schema_version: 1
name: at32f421g8            # 全局唯一：vendor 隐含在仓库命名空间
vendor: artery
version: 0.1.0              # semver
platform: at32              # 平台归属（skill 聚合用，与 chips yaml 的 platform 一致）
status: official            # official | community（由索引仓认定，包内声明无效）
license: SPDX-License-Identifier
requires:                   # ★ 兼容性握手：挂 capabilities.meta 版本体系
  kernel_api: ">=1"         # STEP_META/KERNEL_PLANS 自描述版本
  schema_version: 1         # chips yaml 格式版本
# 可选：探测器指纹（见 §5.4，把 adapt.py 厂商表数据化）
vendor_fingerprints:
  gen_dir: gd32cubeide      # 新厂商的图形配置器目录指纹
  syms_var: GD_Defines_Syms
```

### 4.3 安装机制（`elab pkg`，内核侧命令）

```
elab pkg search <关键词>          # 读市场索引仓（GitHub raw / clone 缓存）
elab pkg install artery/at32f421  # 默认从索引解析 source+sha256；也接受 git URL / 本地路径
elab pkg list                     # 已装包 + 版本 + 状态（含与内核握手结果）
elab pkg update [name]            # 按索引更新，重新校验 sha256
elab pkg remove artery/at32f421
```

**落盘位置与隔离**（设计取舍）：安装到 `elab-flow/packs/<vendor>/<pack>/`，
`Config` 增加 `pack_roots` 搜索路径（`services/elab/config.py` 的 chips/projects 装载点扩展），
而不是把文件直接合并进 `chips/`：

- 好处：卸载干净、一包一版本可 pin（`packs/<…>/.installed.json` 记 version/sha/来源）、
  不污染骨架仓的受控目录；
- `chips/st`、`chips/artery` 保留在骨架仓内作为**内置官方包**（离线可用、单仓开发不受影响），
  同时以相同 pack 格式发布到市场——"官方包 = 首批上架包"，对格式是最好的自吃狗粮。

安装后的自动动作：`elab skill` 重生成（skillgen 已按 `platform` 聚合，天然支持多包共存）→
`elab doctor` 报告该芯片就绪状态（缺工具链/探针时给出 host.yaml 引导）。

### 4.4 分层边界不受影响（硬约束复核）

- 适配包 100% 落在**业务层**（chips 数据 + components 端口），与 AGENTS.md 的分层规则一致；
- DSH 面板若要做"市场"入口：内核在 loopback HTTP ICD 上暴露 `/api/packs`
  （列表/安装状态/搜索结果），**插件只渲染，不解析包格式**——与 `capabilities.meta`
  的自描述模式同构，`boundary.test.mjs` 门禁继续成立；
- 工具层不需要为新包写任何兼容分支（内核过旧 → meta 缺失 → 面板提示同步，规则不变）。

### 4.5 与 CMSIS-Pack 的关系（加分项，非依赖）

ST/Artery 官方都在发 CMSIS DFP（本机 `elab.host.yaml` 的 `svd_roots` 已经指向 DFP 的 SVD 目录）。
适配包的 `debug.svd` 字段已设计为"只声明文件名、目录由 host 提供"——未来 pack 可声明
`svd_source: cmsis-dfp://STMicroelectronics/stm32f4xx_dfp`，复用 CMSIS 分发渠道而不搬运 SVD。
**不做强绑定**：elab-pack 的价值在闭环编排（adaptor/provenance/doctor/CI），与 DFP 是互补关系。

## 5. 交付可行性逐项评估

| 维度 | 判定 | 依据 |
|---|---|---|
| 适配可拆性 | ✅ 已成立 | 适配 = 纯数据 + 可选 C 端口，内核零 per-chip 业务分支（§2.2） |
| 包格式 | ✅ 低风险 | 直接沿用现有 `chips/*.yaml` 格式，新增 `pack.yaml` 一层壳 |
| 安装链路 | ✅ 小改造 | `Config` 加 `pack_roots` + 新 `pkg` 子命令；skill 重生成/doctor 均已存在 |
| 市场索引 | ✅ 零服务器 | Obsidian 模式：索引仓 + PR 上架；dsh 现阶段同样无服务端 |
| 分发 | ✅ 零服务器 | git tag / GitHub Release / tarball + sha256 |
| CI 准入 | ✅ 复用 | `ci/matrix.yaml` 的 `host-gate`（doctor_deep + 全芯片编译）云端可跑 |
| 兼容性握手 | ✅ 已有底座 | `capabilities.meta` 版本体系（§16 已落地）扩展 `requires` 校验 |
| 安全 | ✅ 风险面小 | 包内无脚本/无预编译二进制（C 端口由用户工具链现场编译），schema 校验 + sha256 |
| 法务 | ⚠️ 需核查 | 官方包模板避免再分发厂商 SDK；社区包强制 SPDX 声明（§7.4） |
| 运营 | ⚠️ 长期项 | 社区生态冷启动、质量分层、维护承诺（§7.5）——技术之外的真正瓶颈 |

**总判定：技术交付可行，MVP 不需要任何服务端投入；主要不确定性在生态运营而非工程。**

## 6. 分阶段落地路径

### M1：包机制内核化（本仓，估 1–2 周）

- 冻结 `pack.yaml` schema v1 + `packs/` 落盘布局 + `Config.pack_roots`；
- 实现 `elab pkg install/list/remove`（先只支持 git URL / 本地路径 / 内置包识别）；
- 把 `chips/st`、`chips/artery` 双轨化：仓内保留（内置包）+ 按相同格式打成可发布目录；
- 测试：pkg 安装→skill 重生成→doctor 通过→`elab ci` host-gate 绿。

### M2：市场索引仓 + 上架流程（估 1–2 周）

- 新建 `elab-market` 索引仓：`market.json`（name/version/source/sha256/requires/status/license）；
- PR 上架 + GitHub Actions 自动校验：schema 校验 → 拉包安装 → `elab ci` host-gate 干跑 →
  哈希回填（Obsidian 的目录模式 + 我们的编译门禁，比纯目录审核更强）；
- 提供 `elab-pack-template` 模板仓 + 《适配包贡献指南》（把 §2.3 的 adapt/skill/doctor/ci
  流程写成社区文档）。

### M3：搜索/更新 + 面板入口

- `elab pkg search/update` 联网读索引；`requires` 与 `capabilities.meta` 握手强化
  （内核过旧/过新的双向提示）；
- 内核 ICD 加 `/api/packs`，DSH 面板加市场页（只渲染内核给的数据，遵守分层）。

### M4：生态运营

- 官方包扩容（gd32 等）；`status: community` 质量分层与下载统计（GitHub API）；
- 可选：官方包 cosign 签名；CMSIS DFP 互操作（§4.5）；工具链包化（参考 PlatformIO
  toolchain 包，解决"新芯片要新工具链"的主机配置成本）。

## 7. 风险与缓解

1. **供应链安全**：包格式**硬性禁止**可执行内容（无安装脚本、无预编译二进制、无 pip/npm 依赖）；
   C 端口是源码、由用户工具链编译，可审阅；索引带 sha256，安装时强校验；官方包可加签名。
   这一定位使我们的风险面显著小于 VS Code 那类可执行插件市场（2025 Shai-Hulud 事故的教训）。
2. **兼容性漂移**：内核 schema 演进 → 包失配。靠 `requires.kernel_api` + `schema_version`
   双字段安装时校验；失配给明确的"升级内核 / 固定旧包版本"指引，不静默降级。
3. **质量参差**：索引 status 分层（official/community）+ CI 编译门禁是硬准入（装得上、编得过
   doctor_deep 才能上架）；上板（onhw-gate）对社区包设为可选声明项。
4. **厂商 SDK 版权**：`examples/` 内嵌的 SDK（ST HAL、Artery 库）**不应随包再分发**。
   规则：包只带 chips 数据/端口/模板；SDK 由用户从厂商渠道获取，doctor 检查到位即可；
   社区包 `pack.yaml` 强制 SPDX `license` 字段，索引 CI 拒绝无声明者。
5. **社区冷启动**：官方包先把"获取-安装-闭环"体验跑通（自吃狗粮）；贡献指南以
   `elab adapt` 的确定性探测为卖点（贡献者不需要懂内核，只需要对着厂商工程跑探测 + 补 chip.yaml）。
6. **探测器覆盖**：`adapt.py:50` 的厂商指纹表是内核里唯一的 per-vendor 点。
   M1 可先保持表内维护；若社区包需要新厂商探测，把 `vendor_fingerprints` 移入 pack.yaml
   （§4.2 已预留字段），使探测器同样数据化、随包分发。

---

## 8. 结论

**可以做，且比预想的近：本仓的分层纪律（L1 芯片数据层、内核自描述、adapt 确定性适配、
ci 干跑门禁）恰好就是"适配包化"需要的全部底座**——市场化本质上是给现有数据格式补一条
"索引 + 安装 + 校验"的分发链路。推荐：M1 内核化包机制 → M2 GitHub 索引市场（零服务器）→
M3 面板入口 → M4 生态运营。官方 st/artery 包作为首批上架包兼格式验证。
