## 二、P0 / P1 详述

### 1（P0）历史 run 被全量重放，而且每 2 秒重放一次

**证据**

- `services/elab/kernel/events.py:529` `list_runs()` 对**每个** `r-*.jsonl` 做
  `events = list(replay(p, 0))` —— 只为了拿首行的 `run/start` 和末行的 `run/end`，
  却把整个文件解析成事件列表。无缓存、无 limit。
- `cockpit/web/src/App.tsx:242` 每 **2000 ms** 调一次 `api.runs()`
  （目的只是拿 `active`，即「agent 有没有在别的工程起跑」）。
- `cockpit/web/src/App.tsx:174` 每次切工程也调一次。

**实测**（用真实 run 文件复制成 N 份，直接量 `list_runs`）

| 历史条数 | `list_runs` 耗时 |
|---|---|
| 50 | 124 ms |
| 200 | 581 ms |
| 800 | **2086 ms** |

单条样本只有 3.8 KB / 12 行事件。真实项目的 run 会有更多步骤（首尾更长），
且 `.jsonl` 之外还有 `.log` / `.proc.jsonl` 不参与扫描（这点是好的）。

**后果链**

1. 每天 30 次构建 → 一个月 ~900 条 → 单次扫描 ≈ 2.3 s；
2. 轮询周期是 2 s，**扫描比周期还慢**；
3. `App.tsx:242` 的轮询**没有防重入**（对比 `useSerialStream` 有 `busyRef`），
   于是请求会并发堆积；
4. 内核对每个请求起一个线程做全量 IO + JSON 解析 → CPU 与磁盘持续打满，
   切工程、开面板跟着变慢。

**为什么现在没暴露**：这台机器上只有 1 条历史 run。这是定时炸弹，不是当下故障。

**修法（三层，可分开做）**

| 层 | 做法 | 收益 |
|---|---|---|
| a | `list_runs` 只读**首行 + 尾行**（`run/start` 恒为第一行、`run/end` 恒为最后一行，已实测确认），不再 full replay | 800 条 2086 ms → 约 20 ms |
| b | 轮询改用轻量接口：`GET /api/runs?only=active`（或新增 `/api/runs/active`），**不扫盘**，只返回内存里的 `_active` | 轮询开销归零 |
| c | 加 `?limit=` 与「清理历史」能力（见 #11） | 长期可维护 |

**建议先做 b**（改动最小、立刻消除轮询开销），再做 a。

### 2（P1）WebUI 的 `fetch` 没有超时，也没有取消

**证据**：`cockpit/web/src/api/client.ts:76` 的 `req()` 是**所有** API 的唯一入口，
`fetch(path, {...})` 没有 `AbortSignal`。全仓 `cockpit/web/src` 共 10 处 `fetch`，
`AbortController` / `signal` 出现 **0 次**（插件侧代理层有 30 分钟超时，那是长连接透传，另说）。

**触发场景**（真实存在，非推演）

- `POST /api/debug/session`：openocd 启动等待上限 **20 s**（`debugsession.py:303`），
  探针被别的进程占着时要等满；
- `POST /api/serial/frames/learn`：大样本 1~2 s；
- 内核被强杀/重启中：请求直接挂到 TCP 超时（默认几分钟）。

**为什么这条重要**：HTTP/1.1 下同一域名浏览器只给 6 个并发连接（Chrome）。
一个挂住的请求就吃掉 1 个；串口工作区那 4 个轮询（#4）+ 2 条 SSE（#3）会把它推过 6，
于是**其它所有 API 请求排队**——用户看到的现象是「整个界面点了没反应」。

**修法**：`req()` 加 `signal: AbortSignal.timeout(ms)`，默认 15 s，
长任务端点（debug open / learn）单独放宽到 60 s，超时抛
`ApiError("client-timeout", "请求超时（15 s），内核可能正忙或已停止响应")`。
一处改动覆盖全部调用点。

### 3（P1）SSE 连接上限 8，超限后前端只会「重连中」

**证据**

- `cockpit/server.py:72` `MAX_SSE_CONNS = 8`；超限返回 503
  （`server.py:3168` / `3212`）。
- `cockpit/web/src/debug/DebugWorkspace.tsx:158` **组件挂载就建壳层 SSE**
  （`new EventSource("/api/debug/events")`），与有没有会话无关。
- 每个 pane 再建一条过滤流（`DebugWorkspace.tsx:510`），最多 2 个会话。

**实测**（对同一内核并发开 10 条 `/api/debug/events`）

```
第 1..8 条 → 200 已建立
第 9 条   → 503 {"error":"SSE 连接数已达上限（8）"}
第 10 条  → 503 同上
```

**问题在于**：`EventSource` **读不到 503 的 body**，只会触发 `onerror` 并按 3 s 间隔
无限重连。我们的 `sse.ts:110` 在 `onerror` 里只把状态切成 `reconnecting`。
于是用户看到「一直在连接中」，日志/调试事件静默停更，**没有任何线索指向「连接数已满」**。

**触发场景**：每个标签页 = 1（壳层）+ 2（两个会话 pane）= 3 条；开 3 个标签页
（一个看日志、一个看调试、一个看串口）就 9 条 → 第 9 条永久失败。

**修法**

1. 前端：壳层 SSE 改成**只在有会话时**建（或退化为 3 s 轮询 `GET /api/debug/session`，
   只拿会话清单）；`onerror` 且 `readyState === CLOSED` 时显示
   「事件流断开（可能是连接数已满，关掉其它标签页）」——**至少让人知道**；
2. 后端：上限提到 16，并按 `debug_session` 去重（同一会话多条连接只留最新）。

## 三、P2：体验优化

### 4. 串口工作区每 500 ms 发 4 个请求

`cockpit/web/src/serial/useSerialStream.ts:31` `SERIAL_POLL_MS = 500`，
每拍并发 `monitor` + `bytes`（必发）以及条件触发的 `issues` + `decoded`（`168-256` 行）。
有 `busyRef` 防重入（这点是对的），但稳态仍占 2~4 个浏览器连接。

**修法**：后端加一个合并端点 `GET /api/serial/monitor/poll?line=&byte=&issue=&dec=`，
一次返回四份增量 → 连接占用从 4 降到 1，延迟反而更低。属于中等改动。

### 5. 调试工作区无会话也建 SSE

见 #3 的证据。单独列出来是因为它**白占名额**：面板开着没开会话，也吃 1 个。

### 6. `elab --root X list` 报错误导

```
$ elab --root C:/nope list
elab: error: argument cmd: invalid choice: 'C:/nope' (choose from 'list', 'doctor', ...)
```

`--root` 是**子命令级**参数（`elab list --root ...`），但用户直觉会写在前面。
报错说「invalid choice: 'C:/nope'（可选 list, doctor…）」——用户明明敲了 `list`，
完全对不上。**修法**：把 `--root` 提到全局 parser（子命令仍保留），或至少
在 `invalid choice` 时检测「这个值看起来像路径」并给出正确写法。

### 7. 长请求没有取消/重试

`/api/debug/session`（20 s）、`learn`（1~2 s）、`pkg install`（下载）都是同步等待。
界面只有「忙」，没有「取消」。内核侧的作业类操作（build/run/widget/pkg job）都有
cancel，**唯独这几条同步路径没有**。修法：要么改成作业 + 轮询，要么至少配 #2 的超时
与一个「超时后重试」按钮。

## 四、P3：健壮性隐患

### 8. CLI 只捕获 `ElabError`

`services/elab/__main__.py:293`
```python
try:
    return _dispatch(args)
except ElabError as exc:
    print(f"[elab] 错误：{exc}", file=sys.stderr)
    return 1
```
大部分路径都规规矩矩转成了 `ElabError`（实测：未知工程、根不存在、串口打不开，
文案都带原因和对策，质量很高）。但只要有一个 `KeyError` / `OSError` 漏出去，
用户就看到完整 traceback。建议补一层 `except Exception`：
打印人话 + 「设 `ELAB_TRACE=1` 看栈」。

### 9. `KNOWN_TOPICS` 是三处手工镜像

`services/elab/kernel/events.py:53`（服务端）、
`packages/cockpit-ui-core/src/icd.ts:58`（前端 + 插件各一份）。
`EventSource` 必须**按名 `addEventListener`**，所以服务端新增一个 topic 而前端没加，
那类事件会**静默丢失**（不会报错、不会走 `onmessage`）。
建议加一条测试：从 `icd.ts` 正则抽出列表，与 `events.py` 的 `KNOWN_TOPICS`
∪ `{proc/stdout-batch, stream/closed}` ∪ `debug/*` 比对，不一致就失败。

### 10. `LogRing.push(...lines)` 的展开传参

`packages/cockpit-ui-core/src/log-buffer.ts:104` `this.buf.push(...lines)`。
单批行数极大时会踩 V8 的参数个数上限（约 6.5 万）报 `Maximum call stack size exceeded`。
当前服务端 `proc/stdout-batch` 是 100 ms 合并帧，实际远小于该量级，
所以只是理论风险。改成 `for` 循环或 `concat` 即可消除。

### 11. 没有「清理历史 run」的入口

`runs` 目录只增不减（`grep prune` 只命中 `pkg.prune_skills`，与 run 无关）。
与 #1 同源。建议在 `elab` 里加一条 `elab runs prune --keep 50 --days 30`，
面板上也给个入口（放在「已安装/工具」页签即可）。
