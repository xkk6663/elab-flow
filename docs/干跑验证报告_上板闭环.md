## 2. 本轮新增的两个命令

### 2.1 `elab loop -p X` —— 一键闭环

把四步串起来，任一步失败即中止并返回非 0。`--dry-run` 停在 build，`--no-debug` 跳过第 4 步。
这是"闭环"这个抽象概念**第一次变成一条可执行命令**。

### 2.2 `elab ci` —— 跑 CI 矩阵

读 `ci/matrix.yaml`，**本地与云端共用同一份流程定义**。实测输出：

```
[ci] ▶ host-gate  (环境体检 + 深度漂移校验 + 全芯片编译（云端可跑）)
[ci]   [✓] at32_test    doctor_deep    全绿
[ci]   [✓] at32_test    build          FLASH 7.39% RAM 9.62%
[ci]   [✓] stm32_test   doctor_deep    全绿
[ci]   [✓] stm32_test   build          FLASH 57.65% RAM 42.54%
[ci] —— 跳过 onhw-gate（上板门禁，需 --onhw）

  [✓] host-gate
  [—] onhw-gate  (上板门禁（需 --onhw）)

[elab] ✓ CI 通过
```

```
$ ./elab ci --onhw --job onhw-gate
[ci]   [✓] at32_test    flash          ok
[ci]   [✓] at32_test    debug_verify   Breakpoint 1, main () at .../main.c:78
  [✓] onhw-gate
```

**两档设计的理由**：云端 runner 没有探针，`onhw-gate` 若默认真跑必然失败。
故 `onhw-gate` 标记 `optional: true`，需要显式 `--onhw` 才执行 —— 让"没有硬件"成为
**已知的跳过**，而不是**看起来像失败的红灯**。

## 3. L0 可替换性：一次实证

这是本次最值得记录的一点。"不依赖主机"此前只是**设计主张**，
现在有了可复现的证据：

```
$ ELAB_HOST=ci/host.ci.yaml ./elab build -p stm32_test --dry-run
cmake -S .../STM32_TEST -B .../.work/stm32_test -G Ninja
      -DCMAKE_MAKE_PROGRAM=/usr/bin/ninja          ← 变成 Linux 侧
      -DCMAKE_TOOLCHAIN_FILE=.../toolchains/gcc.cmake
      -DELAB_ARM_GCC_ROOT=/usr                      ← 变成 Linux 侧
      -DELAB_CPU=cortex-m3 -DELAB_FPU=none ...
```

**同一份 `elab`、同一份 `toolchains/gcc.cmake`、同一份 `projects/*.yaml`、同一份 `chips/*.yaml`**，
只换了环境变量指向的另一份 `elab.host.yaml`，整条流水线的路径就整体切换到 Linux 侧。

> 注：`toolchains/gcc.cmake` 用 `CMAKE_HOST_SYSTEM_NAME` 判断要不要加 `.exe`，
> 所以连工具链文件本身也是主机无关的。

**这也顺带解释了为什么 L0 必须是"一份文件"**：它是整条流水线里**唯一**的主机假设来源。

## 4. M5：per-chip skill 由数据生成

```
$ ./elab skill --all
[elab] ✓ 生成 skill：.../skills/artery/at32f421g8/SKILL.md  (2789 B)
[elab] ✓ 生成 skill：.../skills/st/stm32f103xb/SKILL.md  (2813 B)
```

生成的 SKILL.md 包含：芯片身份表、接入工程、闭环命令、**坑位**、验收清单、排障顺序。
其中「坑位」一节的内容源是 `chips/*.yaml` 里新增的 `pitfalls:` 段 ——
**AI 要读的提示，和 doctor 要校验的参数，来自同一份 YAML**。

这样设计的原因：如果 skill 手写，芯片参数一改，skill 就会悄悄过期，
于是 AI 会拿着过期的参数去改代码 —— 这类失败非常隐蔽。

> **清理**：本轮删除了早先手写的 `docs/skills-template/`（`agent_created: false`）。
> 它和自动生成版描述同一颗芯片，属于**双源**；留着必然出现"两份 skill 哪个对"的问题。

## 5. SVD 接入：沿用 openocd cfg 的同构做法

SVD（寄存器视图）的路径是**主机相关**的，但它又是**芯片属性**。若在 `chip.yaml` 里写绝对路径，
就把主机假设泄漏到了芯片层。故沿用 openocd cfg 的既有模式：

| 层 | 写什么 | 例 |
|---|---|---|
| `chips/*.yaml` | **只写文件名**（主机无关） | `svd: AT32F421xx_v2.svd` |
| `elab.host.yaml` | 搜索根（主机事实源） | `svd_roots: [...]` |

实测两份都解析成功：

```
[OK] chip.at32f421g8.svd   AT32F421xx_v2.svd → .../AT32F421G8U7_WorkBench/svd/AT32F421xx_v2.svd
[OK] chip.stm32f103xb.svd  STM32F103.svd      → .../stm32f1xx_dfp/1.1.0/SVD/STM32F103.svd
```

> 实测发现：AT32 的 SVD **不在 `at32-tools` 里**，只在 WorkBench 原件目录
> `Desktop/AT32/AT32F421G8U7_WorkBench/svd/` 下；STM32 的在 STM32Cube 的 DFP pack 里。
> 这类"主机的哪一份副本才是真的"问题，正是 L0 存在的意义。

## 6. 本轮新增约束

| # | 约束 | 依据 |
|---|---|---|
| **C12** | **`elab flash` 必须回显 openocd 的证据行**（`Programming Finished` / `Verified OK`） | 首版只打一行 `✓ 烧录完成`，把最关键的校验结果吞掉了 —— 用户无法判断"到底写没写进去"，等于把证据换成了信任 |
| **C13** | **必须提供非交互 debug 自检（`--verify`）** | 交互式 gdb 无法进 CI，也无法"证明"调试链路通。`--verify` 用 `gdb -batch` 断到 main 后打印证据再退出 → 调试闭环变成了**可断言的一步** |
| **C14** | **openocd 后台进程必须确保清理** | `elab debug` 会 `Popen` 一个 openocd 占住 3333 端口；必须 `finally: terminate()`，否则下一次连接失败 |
| **C15** | **SVD 用"chip 声明文件名 + host 声明搜索根"**，禁止在 `chips/*.yaml` 写主机绝对路径 | 与 openocd cfg 同构；保持 L1 主机无关 |
| **C16** | **CI 与本地必须共用同一份 `ci/matrix.yaml`** | 两处各写一遍流程，必然出现"本地绿、CI 红" |
