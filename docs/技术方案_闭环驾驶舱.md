# elab-Flow 闭环驾驶舱 · 技术方案探究

> 目标：一个界面看清 **agent 此刻在哪一步**，并把 **编译 / 烧录 / 日志 / 串口回读** 收在同一条时间线上；
> 能选 `examples/` 里的工程一键跑，也能手动干预每一步。
> 设计原则照抄 DeepSeek Harness —— **万物皆插件（Everything is a plugin）**，可卸可换。

状态：**技术方案探究 v3（五项决策已定 + 选型深挖 + 一键适配讨论）** · 日期：2026-10-04 · 依据：本仓库 L0~L6 实测代码 + DSH 源码实读 + 本机环境探测

---

## 0. 一页纸结论

| 问题 | 结论 |
|---|---|
| 能不能做？ | **能。而且不需要推翻现有架构。** |
| 最大的利好 | elab 现有 `flash/build/debug/ci` **每个函数都接受 `log=` 回调**，且**全部返回 dict** —— 这正是一条现成的"事件流 seam"。驾驶舱不改工具链核心，只把 `log=print` 换成 `log=emit`。 |
| 最大的缺口 | ① **无流式**（`subprocess.run` + `capture_output`，编译时看不到进度）；② **串口完全未实现**（`§11 已知限制` 明写 `elab monitor ❌ 未实现`）；③ **零依赖与 pyserial 冲突**。 |
| 关键决策 | 见 §7 —— **五项已定**。核心是：**长任务必须独立进程 + 事件流分离**，否则 `subprocess.run` 会把唯一 Python 线程钉死，SSE 断流，驾驶舱"死"给你看。 |
| 前端路线 | **仿 DSH 的独立前端工程**：React 18 + TypeScript + Vite + CSS Modules + `--elab-*` 令牌；**运行时不依赖 Node**（`dist/` 由 Python 标准库直接托管）。见 §15。 |
| 工作量 | M1 驾驶舱骨架 **3–4 天**；M2 手动干预 +1 天；M3 串口闭环 +2 天；M4 插件化收敛 +1~2 天。 |
| 风险等级 | 低（无系统级改动、无业务代码改动）到中（前端构建链、串口依赖、Windows COM 探测）。 |

**一句话**：驾驶舱不是加一个新框架，而是给已存在的 `log=` seam 装上一块"屏幕"，再顺手把漏掉的 `monitor` 补齐。

## 1. 需求解构

### 1.1 用户原话拆成可执行条目

| # | 需求 | 类型 | 归属里程碑 |
|---|---|---|---|
| R1 | 清晰看到 **agent 此刻在做哪个步骤** | 状态机 / 时间线 | M1 |
| R2 | 看 **编译情况**（进度、错误、内存占位） | 流式日志 | M1 |
| R3 | 看 **烧录情况**（openocd 证据行、verify 结果） | 流式日志 | M1 |
| R4 | 看 **日志情况**（工具链全过程日志） | 流式日志 + 归档 | M1 |
| R5 | 看 **串口闭环回来的日志**（板子打印回读） | 新增能力 | **M3** |
| R6 | 选 `examples/` 指定工程做编译等操作 | 工程选择器 | M1 |
| R7 | **一件皆是插件**的架构 | 内核设计 | M4（但 M1 起就按此分层） |
| R8 | **可手动干预**：手动编译 / 烧录 / 监测串口 | 手动触发 | M2 |
| R9 | 一个界面完成所有芯片工具链流程 | 驾驶舱整屏 | M1~M2 |
| R10 | **UI 上"一键适配工程"**：图形配置器导出的 CMake 工程 → 一键接入 elab-Flow | 探测 + 声明 + 验收 | **M5（新增）**，见 §19 |

### 1.2 需求里没写、但必须替用户想清楚的

- **R5 的"闭环"指什么**：串口回读让 `烧录完成` → `板子真的在跑并打印` 之间的空白闭合。这是 §9 里 AT32 的"已验证"和 STM32 的"未验证"之间那道缝。
- **R8 的"手动干预"边界**：本方案按**按钮即触发**设计（不阻塞流水），预留"步骤重跑"。
- **R1 的"agent"是谁**：目前在这个仓库里，"agent" 就是 `elab ci` / `elab loop` 那条流水。所以"看 agent 在哪一步" = **看流水线状态机**，不是看大模型思考。这点很重要，避免把驾驶舱做成聊天 UI。

| **`plan.shell_preview()`** | `plan.py` | 手动干预的 `--dry-run` 预览现成 |

### 3.2 缺口（必须新建的东西）

| # | 缺口 | 证据 | 影响 |
|---|---|---|---|
| G1 | **无流式**：`subprocess.run(capture_output=True)` 阻塞到结束 | `builder.py:207 _run`、`flash.py` | R2/R3/R4 的"实时"无法满足 |
| G2 | **串口未实现** | `§11`：`elab monitor ❌ 未实现`；`config.py` 只有 `serial()` 读 YAML | R5 整条缺失 |
| G3 | **零依赖 vs pyserial** | 本机 `import serial` → `ModuleNotFoundError` | 已决策：可选依赖 + 降级（§18） |
| G4 | **没有跨进程运行态** | 现状"跑完即返回" | 无法"取消"、无法看"正在进行的那次" |

## 4. 架构设计

### 4.1 分层总览（在现有 L0~L6 上加 L7 驾驶舱）

```
┌─────────────────────────────────────────────────────────────┐
│  L7  cockpit（驾驶舱）  ← 新增                                │
│   ├─ cockpit/server.py    零依赖 HTTP + SSE（stdlib）          │
│   ├─ cockpit/web/         独立前端工程（React+TS+Vite）        │
│   └─ profiles/*.yaml      插件清单（有序层，可 patch）         │
└───────────────┬─────────────────────────────────────────────┘
                │ 订阅 elab/event（只追加 JSONL）
┌───────────────▼─────────────────────────────────────────────┐
│  L6 event stream（事件流）  ← 新增，是"投影源"不是"投影"        │
│   emits: run.start / step.start / proc.line / step.end / ...  │
└───────────────┬─────────────────────────────────────────────┘
                │ 同一份 log= seam（★ 现有代码几乎不动）
┌───────────────▼─────────────────────────────────────────────┐
│  L3 services/elab（现有） builder / flash / doctor / ci       │
│   └─ 每个函数都接受 log=、返回 dict  ← 这就是接缝            │
└───────────────┬─────────────────────────────────────────────┘
   L0 host / L1 chips / L2 toolchains / L4 projects / L5 ci
```

### 4.2 内核：`services/elab/kernel/`（照抄 Cordis 的最小内核）

| Cordis (DSH) | elab cockpit | 说明 |
|---|---|---|
| `ctx.sessions` | `ctx.events` | 只追加事件日志 + 内存索引 |
| `ctx.tools` | `ctx.runner` | 作用域"步骤执行器"（build/flash/debug/monitor） |
| `ctx.agents` | `ctx.runs` | 活动 run 注册表 + `run/*` 事件 |
| `ctx.llm`（adapter seam） | `ctx.serial`（后端 seam） | 串口后端可替换（pyserial / ctypes / fake） |
| `ctx.slots` | `ctx.views` | 前端视图贡献点 |
| — | `ctx.projects` | 读 `projects/*.yaml` 的工程目录 |
| `ctx.layout` | `ctx.layout` | 视图状态（三列宽度、当前 tab）—— 同名，同义 |

最小内核 API（**有意保持极小**）：

```python
class Ctx:
    def provide(self, key, obj): ...          # 贡献服务
    def get(self, key): ...
    def mount(self, plugin) -> Handle: ...    # 挂载；apply(ctx)
    def effect(self, teardown): ...           # ★ 注册可逆副作用
    def emit(self, topic, payload): ...        # typed 事件
    def on(self, topic, fn) -> Handle: ...
```

**"effects unwind on unload" 的落地要求**（对应 DSH "no privileged core"）：

| 插件 | 卸载时必须 unwind |
|---|---|
| `run-manager` | terminate 所有子进程、关掉所有 SSE 连接 |
| `serial-monitor` | **关串口**（否则下次打不开）、停读线程 |
| `flash` | 杀掉 openocd 后台服务（`flash.debug` 已有 `finally terminate()` 先例，C14） |
| `web-ui` | 解除静态目录挂载 |

> ⚠️ **硬约束**：`subprocess.run` 不是效果，**`Popen` 才是**。所有长任务必须 `Popen` 并登记到 `ctx.runs`，否则卸载时无句柄可杀 → 孤儿进程占住 3333 端口 / COM 口。

### 4.3 事件模型（只追加，驾驶舱的唯一真相）

| 域 | 前缀 | 是否持久 | 例子 |
|---|---|---|---|
| **Run 事件** | `run/*` | ✅ 追加 JSONL | `run/start`、`run/step-enter`、`run/step-exit`、`run/end`、`run/cancel` |
| **Activity 事件** | `proc/*` | ❌ 内存 only | `proc/stdout`、`proc/stderr`、`proc/exit` |
| **Capability 事件** | `serial/*`、`fs/*` | 半持久 | `serial/line`、`serial/open`、`serial/close`、`serial/error`、`serial/closed-loop` |

`run/*` 的 JSONL 形状（**一个事件一行，永不改**）：

```json
{"ts":1759570000.123,"run":"r-7f3a","topic":"run/step-enter","seq":12,
 "step":"build","project":"at32_test","actor":"agent"}
{"ts":1759570001.456,"run":"r-7f3a","topic":"proc/stdout","seq":13,
 "step":"build","line":"[12/28] Building C object ..."}
{"ts":1759570003.789,"run":"r-7f3a","topic":"run/step-exit","seq":14,
 "step":"build","ok":true,"detail":"flash 7.39% ram 9.62%",
 "artifacts":{"elf":{"path":".work/at32_test/TEST.elf","bytes":7444}}}
```

**关键设计**：

1. **`seq` 单调递增** —— 回放与"断线重连追上"的唯一依据（DSH 的 `stateOf()`/`snapshot()` 同思路）。
2. **`actor`: `agent` / `human`** —— 直接回答 R1："这一步是 agent 干的还是我点的"。
3. **`proc/*` 不落盘** —— 编译输出动辄几 MB。只保留**环形缓冲**给 UI；落盘只留 `run/*` + step 摘要行（对应现有 `builder._tail(n=25)` 从"结尾 25 行"升级为"实时环形 + 结束落摘要"）。
4. **归档**：`.work/.cockpit/runs/<run-id>.jsonl` + 每 run 一份 `.log`（合并 stdout/stderr 供 grep）。
   - 遵循 DSH "committed paths are never renamed"：**新 run = 新文件，绝不复写**。

### 4.4 插件清单与有序层（照抄 Profile/Bundle）

`cockpit/profiles/web.yaml`：

```yaml
profile: web
layers:                          # 层序即挂载序；后者可覆盖前者
  - plugins/projects.yaml        # 工程源（projects/*.yaml + examples/）
  - plugins/toolchain.yaml       # 复用 L2 toolchains
```

## 5. 关键机制详设

### 5.1 长任务：独立进程 + 事件流分离（**第一硬约束**）

**问题（G1）**：`builder._run()` 用 `subprocess.run(capture_output=True)`。若把 `elab ci` 塞进后台线程，HTTP 服务会被拖死，SSE 推不出去；`flash.debug` 起 openocd 时还会**阻塞 20s 等端口**。

| 方案 | 做法 | 优点 | 缺点 | 采纳 |
|---|---|---|---|---|
| A. 同进程线程 | `threading.Thread(run_ci)` | 简单 | `subprocess.run` 阻塞、信号难传、崩溃拖垮服务 | ❌ |
| B. 库内 Popen 化 | 把 `_run` 改 `Popen` + 流读 | 事件最干净 | 要动 L3 核心（违"外骨骼不改器官"） | ⚠️ 部分 |
| **C. 子进程 worker + 事件文件** | `elab run --emit-events` 独立进程，父进程只跟读事件 | **解耦、可取消、CLI 与 cockpit 同路径** | 需定义事件文件协议 | ✅ **主选** |

```
cockpit-server(父) ──spawn──> python -m elab run -p at32_test --emit-events
        │                              │
        │                     ① log=emit → 追加 .work/.cockpit/runs/r-xxx.jsonl
        │                     ② 同时把子进程 stdout 兜底 tail
        └──follow(只追加文件)──────────┘
        └──SSE broadcast(父) ──> 浏览器
```

- 父进程**只做**：spawn、跟读只追加文件、转发 SSE、接收"取消"→ `terminate()` 进程组。
- **可取消**：Windows `CREATE_NEW_PROCESS_GROUP` + `taskkill /T`（cmake→ninja→gcc 是一棵树）；POSIX `os.killpg`。
- **CLI 与 cockpit 同路径**：`elab run --emit-events` 终端里也照样能用。
- **回归安全**：新增 `run` 子命令**不改** `build/flash` 既有行为。

### 5.2 步骤状态机（R1 的答案）

复用 `ci/matrix.yaml` 的 job/step 定义：

```
doctor ──► build ──► flash ──► debug_verify ──► monitor ──► [闭环 ✓]
  ✓          ✓         ✓            ✓            ▶ listening
```

四态：`pending / running / ok / failed`（外加 `skipped`、`cancelled`）。
`run/step-enter` / `run/step-exit` 驱动状态迁移 —— **前端不猜状态，只投影事件**。

**"此刻在哪一步"的三种来源，按优先级**：

1. `run/step-enter` 事件（权威）；
2. 兜底：解析 stdout 的 `[3/4] flash` 这类既有进度行（`cmd_loop` 已有此格式）；
3. 再兜底：超时推断 —— 标记为 `inferred`，UI 用**虚线**区分（对应 DSH 的 `TextShimmer` 运行态视觉）。

### 5.3 串口闭环（R5，本方案最大增量）

**闭环语义**：烧录 ≠ 跑起来。`flash` 结束到"板子打印第一行日志"之间必须补上。`monitor` 是闭环的**最后一环**。

| 能力 | 实现 | 依赖 |
|---|---|---|
| 端口枚举 | Windows：`winreg` 读 `HKLM\HARDWARE\DEVICEMAP\SERIALCOMM`；Linux：`/dev/tty{USB,ACM}*` | stdlib |
| **蓝牙口识别** | Windows：关联 `\Device\BthModem*` → **默认排除**（本机 COM3–COM8 全是蓝牙口） | stdlib `winreg` |
| 打开/设波特率 | pyserial（可选依赖，§18） | pyserial |
| 读行 | 后台线程 `readline()` → `serial/line` 事件 | pyserial |
| 写行 | 输入框 → 追加 `\r\n` 或 `\n`（可配） | — |
| 波特率预设 | 读 `elab.host.yaml serial.baud`（默认 115200） | L0 |
| 日志落盘 | `runs/<run>.serial.log`（默认**开**，是闭环证据） | — |
| 断线重连 | `SerialException` → 自动重开（板子复位会掉口） | — |
| 关键字高亮 | `error/fault/assert/hardfault/PANIC` 上色 + 计数 | 前端 |
| **闭环判据** | **声明在 `projects/*.yaml` 的 `monitor.close_on`**，命中关键字即判闭环 | §16 详设 |

**与 L0 的对接**：`serial: {default: auto, baud: 115200}` **早已在 L0 声明**，一直没人消费。驾驶舱就是它等的消费者 —— 无需改 YAML。

### 5.5 推送通道：SSE（已决策 D3）

| 需要 | stdlib 方案 | 可行 |
|---|---|---|
| HTTP 服务 | `http.server.ThreadingHTTPServer` | ✅ |

```yaml
# projects/at32_test.yaml 追加（可选）
monitor:
  close_on:                      # 任一命中即判"闭环成立"
    - { kind: regex, pattern: "^\\[boot\\] ok", within_s: 8 }
```

### 7.1 决策带来的**新约束**（必须写进设计）

| 新约束 | 说明 |
|---|---|
| **N1 前端构建链入仓** | 仓库首次引入 npm 生态。**必须**通过"提交 `dist/` + 产物一致性守卫"保证：**clone 下来不装 Node 也能跑**。见 §15.6 |
| **N2 `--elab-*` 令牌契约** | 前端不硬编码颜色，一律走令牌；否则主题/暗色会碎。见 §15.4 |
| **N3 串口能力协商** | 前端必须先问 `/api/capabilities` 再决定串口 Tab 可用性，**不能假设 pyserial 在** |
| **N4 判据必须有超时** | `close_on` 必须有 `within_s`，否则"板子没起来"会永久挂起 |
| **N5 串口与 openocd 互斥** ★ | DAP-Link/AT-Link 是**复合 USB 设备**：openocd 占着 SWD 接口时，它的虚拟串口**读不了**（`CreateFileW` → `ERROR_ACCESS_DENIED(5)`，连共享模式也拒）。故：**serial 阶段必须在 openocd 完全退出之后**；`loop` 里 serial 与 debug **不可并行**；`monitor` 开串口前应先检查有无残留 `openocd`/`arm-none-eabi-gdb` 进程并给出可操作报错。实测记录见 `.workbuddy/memory/2026-10-04.md` |
| **N6 `.map` 未产出（已于本轮修复 ✅）** | **实为两个成因相反的缺陷**，所以不能靠"保留工程自带的 flag"来修：<br>**【B 类 AT32】** 其 `CMakeLists.txt:22` 在 `project()` **之前** `include()` 自带工具链，`gcc-arm-none-eabi.cmake:41` 把 `-Wl,-Map=${CMAKE_PROJECT_NAME}.map` 放进 `CMAKE_C_LINK_FLAGS`；而 `inject.cmake` 为消除双份 `-T` 而 `unset(CMAKE_C_LINK_FLAGS)` → 顺带清掉了 Map，且无人补回。<br>**【A 类 STM32】** 其工具链只挂在 `CMakePresets.json → toolchainFile` 上，elab 用 `-DCMAKE_TOOLCHAIN_FILE` 接管后该文件**根本不执行** → 从未有过 Map；`inject.cmake` 又整体覆盖 `CMAKE_EXE_LINKER_FLAGS`。<br>**修复定论：Map 是 elab 对 `projects/*.yaml → artifacts.map` 的承诺，就该由 elab 盖章。** 落点由 `plan.py` 显式下传 `-DELAB_MAP_FILE=<abs>`（**不从 `${CMAKE_PROJECT_NAME}` 反推文件名**——`at32_test` 就手写了 `set(CMAKE_PROJECT_NAME TEST)`，基名一旦漂移会静默错位），`gcc.cmake`（L2，覆盖 T1 无 inject 路径）与 `inject.cmake`（project() 后盖章）用同一变量同一段逻辑，两层不会各自漂移。另在 `builder.py` 加"声明了 `artifacts.map` 却未生成 → WARN"，因为原实现在此处**静默忽略**，正是 N6 能长期隐藏的原因。<br>**验收**：三工程均产出 map（`at32_test`/`stm32_test` 为首次产出）；链接行 `-T`/`-Wl,-Map` 各**恰好 1 份**（无双份回归，at32_test FLASH 4840 B 与基线一致）；`doctor --deep` 全绿、`ci` host-gate 绿、`loop` 五步全绿。 |

### 15.5 状态：store + `useSyncExternalStore`（uSES 桥）

DSH 的桥叫 `bindSnapshotSelector`（uSES bridge）。我们照抄**形态**（不抄代码）：

```ts
// store/runStore.ts —— 极简，零依赖
type Snapshot = { run?: RunInfo; steps: StepState[]; logs: LogRing; serial: LogRing };

let snapshot: Snapshot = initial();
const listeners = new Set<() => void>();

export function applyEvent(e: ElabEvent) {           // SSE 事件唯一入口
  snapshot = reduce(snapshot, e);                     // 纯函数归约
  listeners.forEach(l => l());
}
export function subscribe(l: () => void) { listeners.add(l); return () => listeners.delete(l); }
export function getSnapshot() { return snapshot; }    // ★ 必须返回稳定引用（不可变归约）
```

```tsx
// 组件侧：只选自己需要的切片，避免整树重渲染
const steps = useSyncExternalStore(subscribe, () => getSnapshot().steps);
```

| 特性 | 价值 |
|---|---|
| 归约 `reduce(snapshot, event)` 是**纯函数** | 可对同一事件流**回放**出任意时刻的界面（呼应 DSH "replay on the same event stream"） |
| 事件是唯一写入口 | 前端**不可能**与后端状态漂移（对应 "Model-visible means logged"） |
| 零依赖 | 不引入 Redux/Zustand |
| 快照不可变 | `useSyncExternalStore` 的引用相等判断天然正确 |

**日志不入 store（性能关键）**：`proc/*` 高频行**不进 React 树**，走"环形缓冲 + `requestAnimationFrame` 批量刷 DOM"，或直接操作一个 `<pre>` 的 `textContent` 追加。React 只管**骨架与状态**，不管**每行日志**。

### 15.6 构建产物策略（N1/K3/K4 的解法）

**目标**：`git clone` 后**不装 Node 也能跑**；同时**不允许** `dist/` 与源码漂移。

```
开发者：  npm run build  →  cockpit/web/dist/   （提交入仓）
用户：     python -m cockpit.server              →  直接托管 dist/，无需 Node
CI 守卫：  npm ci && npm run build && git diff --exit-code cockpit/web/dist/
           └─ 有差异 → 红灯（"你改了 tsx 但没重新 build"）
```

守卫写法（呼应现有"工作流双源一致性守卫"的同一手法）：

```yaml
# .github/workflows/elab.yml 追加 job: web-dist-guard
- name: 前端产物一致性守卫
  run: |
    npm --prefix cockpit/web ci
    npm --prefix cockpit/web run build
    git diff --exit-code cockpit/web/dist/ \
      || { echo "::error::dist/ 与源代码不一致，请本地 npm run build 后提交"; exit 1; }
```

**代价与取舍（必须写明白）**：

| 取舍 | 说明 |
|---|---|
| 仓库体积增加 | `dist/` 约数百 KB（gzip 后更小），可接受 |
| diff 噪声 | 每次前端改动产生一份打包 diff；用 `.gitattributes` 标 `linguist-generated` 降噪 |
| 换来什么 | **运行时零依赖不变**：只有 Python 也能跑驾驶舱；CI 的 `host-gate`（Python 侧）完全不需要 Node |

> 这是本次决策最需要交代的一处**与 README「零第三方依赖」边界的张力**：我们把"零依赖"的边界**从"构建时"收窄到"运行时"**。这是 D2 选框架的必然代价，且已被上面两条（提交产物 + 守卫）控制住。

## 16. 串口闭环判据设计（D5：读到关键字即判闭环）

### 16.1 语义定义

- **闭环成立（`closed-loop ok`）**：烧录完成后 `within_s` 秒内，串口读到的某一行命中 `close_on` 中**任一**判据。
- **闭环失败（`closed-loop failed`）**：命中 `fail_on`；或超过 `within_s` 未命中 `close_on`。
- **未判定（`inconclusive`）**：串口根本没打开（无设备 / 被占用）—— **不算失败**，UI 明确说"未能监听"，避免把环境问题误报成固件问题。

### 16.2 声明位置（单一真相）

判据写在 **`projects/<name>.yaml`** 的可选 `monitor:` 块（§6 已给样例）。理由：

- 它是**固件行为**的属性，不是芯片属性（不进 `chips/*`）；
- 也不是主机属性（不进 `elab.host.yaml`）；
- elab **不猜**关键字 —— 与 `chip.yaml` 作为"可校验的单一真相"同一思路。

**没有 `monitor.close_on` 时**：`monitor` 降级为**纯监听**（不判闭环），只显示串口流；`StageBand.monitor` 显示 `—` 而非 `✓`。

### 16.3 判据类型

| kind | 语法 | 用途 |
|---|---|---|
| `regex` | `{ kind: regex, pattern: "..." }` | 主力：匹配任意关键字 |
| `contains` | `{ kind: contains, value: "boot ok" }` | 简便写法（内部转义） |
| `line_count` | `{ kind: line_count, n: 5, within_s: 5 }` | "能打印满 5 行"即视为在跑 |

`within_s` 必填（N4），否则不判 —— **防止"板子没起来"永久挂起**。

### 16.4 判据引擎（状态机）

```
        ┌────────────┐  open ok   ┌────────────┐  命中 close_on   ┌──────────┐
start ─►│ connecting │───────────►│  waiting   │─────────────────►│  closed  │ ✓
        └─────┬──────┘            └─────┬──────┘                  └──────────┘
              │ open fail               │ 命中 fail_on
              ▼                          │ / within_s 超时
        ┌────────────┐                   ▼
        │inconclusive│             ┌──────────┐
        │   (—)      │             │  failed  │ ✗
        └────────────┘             └──────────┘
```

每行读到时**同时**检查 `close_on` 与 `fail_on`（**`fail_on` 优先**，避免"先报错后又打印 ok"被误判成成功）。

### 16.5 事件与证据

**实际实现的字段形状**（`run.py` 的 `monitor` 分支 → `serial/closed-loop`）：

```json
{"ts":1791180118.381,"run":"r-ser004","topic":"serial/closed-loop","seq":10,"actor":"agent",
 "project":"at32f421g8u7","verdict":"ok",
 "rule":"regex:^\\[(boot|alive)\\] within_s=10","evidence":"[alive] tick=38",
 "detail":"命中 close_on（regex:^\\[(boot|alive)\\] within_s=10）"}
```

- **`verdict` 是字符串三态 `ok` / `failed` / `inconclusive`，不是 `ok: true/false`**。
  本节初稿写的是 `"ok":true`，那是**错的**：布尔量装不下三态，会把
  "没读到约定关键字"塌成"失败"——正好触犯判据引擎最核心的那条铁律
  （缺证据 ≠ 有失败证据，见 §16.2 与 `monitor.py` docstring）。三态的消费者
  已统一：`run/step-exit.extra.verdict`、`/api/runs.active`、`monitor.py --json`
  用的是同一个词表；本事件的 `verdict` 与它们逐字一致。
- **`rule` / `evidence` 直接取 `judge()` 已算好的 `evidence[0].rule` / `.line`**。
  它们**在 `failed` / `inconclusive` 下允许为空**：没有任何规则被命中时，
  引用一条"命中判据"本身就是假话。`evidence` 为空不代表丢证据——
  `detail` 里始终有 `reason` 原文，且逐行原始证据在
  `<run-id>.serial.log`（给人 grep）+ `serial/line` 事件（给界面）里。
- **`port` / `baud` / `bytes` / `lines` 不重复放在本事件上**：它们是
  `serial/open` 与 `serial/close` 的字段，本事件只承载"判定结论"。
  `elapsed_s` 同样只在 `run/step-exit.extra.serial` 里（含完整 `Verdict.to_dict()`）。
- **必须带 `evidence` 原文**（延续约束 C12："只打摘要等于把证据换成信任"）。
- UI（`StageRail.tsx` 的「串口闭环」段）用 `verdict` 选 Pill 颜色、
  用 `rule` + `evidence` 做悬停展开。

> **本节的教训**：设计文档里的示例 JSON 也是一种契约，但它**没有守卫**——
> 示例里写错的形状会一直躺到有人对着它写实现为止。前端 `runStore.ts` 的
> `closedLoop: {verdict, rule, evidence}` 才是事实来源（它跟实现一起被
> TypeScript 编译器检查），所以这里以实现 + 前端为准回改了文档。

### 16.6 归因到时间线

`monitor` 步骤的 `run/step-exit` 带 `closed_loop: true/false/null`，§5.2 状态带最后一格才有确定语义：

```
doctor ✓ → build ✓ → flash ✓ → debug ✓ → monitor ✓(2.31s)
```

### 16.7 边界与坑

| 坑 | 处理 |
|---|---|
| 板子复位导致 COM 掉口 | 断线重连；重连后**重置 `within_s` 计时**，并记一条 `serial/reconnect` |
| 烧录后需手动复位才打印 | 支持 `monitor.reset_before: true` → openocd `reset run`（需探针）；否则提示人工按复位 |
| `\r\n` vs `\n` | 行模式按 `\r?\n` 切；保留"无换行也超时 flush"兜底 |
| 中文/UTF-8 乱码 | 解码 `errors="replace"`；UI 提供"按 GBK 再解一次"切换（嵌入式常见） |
| 关键字太宽（如 `ok`） | 启动时 lint：pattern 若匹配空串或长度 <3，给 warning |
| 判据命中但板子其实异常 | 这是判据质量问题，不是引擎问题 —— `fail_on` 与 `close_on` 由工程作者共同负责 |

### 16.8 实现记录（`services/elab/monitor.py`，已上板验收）

**状态：§16 的引擎已在 CLI 层落地并实测**。与本章最初设计有 4 处**有意偏差**，逐条记录：

| # | 原设计 | 实现 | 为什么改 |
|---|---|---|---|
| 1 | §16.1："超 `within_s` 未命中 `close_on` → **failed**" | 改为 **inconclusive** | ★ 原文**自相矛盾**：§16.1 第三条自述"不能把环境问题误报成固件问题"，第二条却把"没打印"算成失败。裁决：**`failed` 必须有正面失败证据**（命中 `fail_on`，或"说过话后静默"）。否则"固件没写 printf"会被误报成"固件崩了" |
| 2 | §16.4："每行读到时**同时**检查 close_on 与 fail_on（fail_on 优先）" | `fail_on` **先对整缓冲区全扫**，再谈 ok | "同时检查"实现出来就是"谁先命中谁赢"→ `[alive]` 之后 0.6s 才 HardFault 会被 **ok 早退掩盖成假通过**（由单测用例②/⑨ 抓出并固化） |
| 3 | （未提） | 新增 `monitor.settle_s`（默认 **1.5s**） | 命中 ok 后不立刻收工，再观察一小段 —— 否则"刚报活就崩"同样漏判。代价是判定多花 ~1.5s |
| 4 | §16.7 `monitor.reset_before: true` → 注入 openocd `reset run` | **不采用**；改由 `debug --verify` 收尾 `monitor reset run` | 注入 openocd reset 会**撞上 N5**（openocd 占 SWD 时 VCP 打不开）。改为让上一步自己把板子留成运行态：`flash` 自带 `reset`，`debug --verify` 收尾由 `reset halt` 改 `reset run` |

**判据类型实现情况**：`regex` ✅ / `contains` ✅（`value:` 与 `pattern:` 键都收）/ `exact` ✅ / `line_count` ✅（聚合判据，不逐行 —— 对"关键字未知的第三方固件"是唯一可用判据）。另加 **lint**：正则非法或 `line_count` 缺 `within_s` → 跳过并告警；pattern 能匹配空串或长度 <3 → 告警"判据过宽，容易假通过"。

**退出码约定**（供 CI/agent 消费）：`0=ok`、`1=failed`、`2=inconclusive`。`elab loop` 把 inconclusive 记为 `?` 且**不中断闭环**。

**证据**：命中行原文进 `evidence[].line`（延续 C12），`monitor.run()` 返回可直接 JSON 化的 dict（`elab monitor --json`）；§16.5 的 `serial/closed-loop` SSE 事件属 cockpit（M1/M3）消费同一份 dict。

**N5 实证**：本机 AT-Link 的实例 ID 是 `USB\VID_0D28&PID_0204&MI_01\…` —— **`MI_01` 直接证明它是复合设备的第 1 个接口**（`MI_00` = CMSIS-DAP 调试口，`MI_01` = 虚拟串口），从 USB 拓扑层面坐实了"同一个 DAP-Link，openocd 占 SWD 时 VCP 被独占"。

**软复位已实现且实测可用**：`serialport.restart_device()` 走 `pnputil /restart-device <实例ID>`（实例 ID 由 `PortName` 反查注册表 `SYSTEM\CurrentControlSet\Enum\USB`），暴露为 `elab monitor --reset-port`。本机实测**无需提权**即成功；复位后串口立即恢复、闭环再次命中。另有 `OPEN` 阶段对 `ERROR_ACCESS_DENIED` 做 4×0.6s 重试，失败时给出 N5 解释与可操作建议（`diagnose_denied`）。

**蓝牙口识别**：见 §18.5，已在 `serialport.py` 落地。★ 另发现一个注册表坑：拔插后 `SERIALCOMM` 里会**残留旧映射**（`\Device\USBSER000` 与 `\Device\USBSER001` 同指 COM10），必须按 COM 号去重，否则 `auto` 会误报歧义。

## 17. SSE 事件通道详设（D3）

### 17.1 协议

```
GET /api/events?run=r-7f3a&from=0
Accept: text/event-stream

HTTP/1.1 200 OK
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache

id: 12
event: run/step-enter
data: {"ts":...,"step":"build","project":"at32_test","actor":"agent"}

id: 13
event: proc/stdout
data: {"ts":...,"step":"build","line":"[12/28] Building C object ..."}

: keep-alive                    ← 注释行心跳，15s 一次
```

### 17.2 断线续传（`Last-Event-ID`）

浏览器 `EventSource` **自动**在重连时带上 `Last-Event-ID: <最后收到的 id>`。服务端据此从 JSONL **按 `seq` 重放**：

```python
def replay(jsonl_path, after_seq):
    for line in open(jsonl_path, encoding="utf-8"):
        ev = json.loads(line)
        if ev["seq"] > after_seq:
            yield ev
```

这是"只追加日志"设计的**直接红利**：重放不需额外机制，也不需内存里的历史。
（对应 DSH："Resume, fork, search, and replay all operate on the same event stream."）

### 17.3 心跳与背压

| 问题 | 方案 |
|---|---|
| 空闲时连接被掐断 | 每 15s 发一行 `: ping`（每客户端一个计时器） |
| `proc/stdout` 刷屏 | **100ms 合并**：同一 step 的行攒成 `proc/stdout-batch`（`lines:[...]`），事件数降 1~2 个数量级。★ 合并的对象**只有进程输出**（`events.is_batched`），见下 |
| 慢客户端拖垮服务 | 每连接有界队列（2000 条）；溢出时**丢弃 `proc/*`、保留 `run/*`**，并发 `stream/overrun` 让 UI 提示"日志已截断" |
| 客户端太多 | 本地单用户，忽略；但仍设上限（如 8 连接） |

**三条实现要点**（都是实测换来的，别简化掉）：

1. **合并判据不能是 `is_activity()`**。前者是**传输层**规则、后者是**落盘通道**分类，范围差得远。
   用错判据的后果：`serial/open` / `serial/close` / `serial/closed-loop`（都**没有** `line` 字段）
   被合并成一行**空文本** → 整条串口链在**实时**路径静默消失，而 REST 回放逐条成帧
   （"刷新页面反而正常"）。现为 `is_batched()` = 只有 `proc/stdout|stderr`。详见 ICD §3.4 / 约束 C24。
2. **`stream/overrun` 必须在去重之前成帧**。它带的 `seq` 是**定位锚点**（当前游标），
   必然 `<= Last-Event-ID` —— 放在去重之后，这条"告警"会被自己的去重逻辑吃掉。
   发帧时**不带 `id:`**：它不是 run 的序号，写进 `Last-Event-ID` 会让重连游标越过它自己。
3. **`stream/closed` 与 `run/*` 同级不可丢**。它的 `is_activity()` 也是 `True`（前缀 `stream/`），
   队列满时会被当可丢事件丢掉 —— 而它是浏览器**唯一**的"run 结束了"信号。
   丢了它，`markStreamClosed` 永不触发、界面**永远显示"运行中"**，
   唯一兜底是心跳分支（`heartbeats > 8` ≈ 2 分钟）后断开重连。
   症状是"卡住"而不是"报错"（约束 C25）。

### 17.4 事件与 CLI 人读输出的关系

**事件是唯一真相**：

- 子进程 `elab run --emit-events` 里，`log=emit` 把**同一份**事件同时（a）追加 JSONL、（b）以人类可读格式打到 stdout。
- 于是"终端里看到的"和"界面上看到的"是**同一份事件的两种渲染**，不可能漂移（K8 的解法）。

### 17.5 取舍记录

| 项 | SSE | WebSocket |
|---|---|---|
| 实现成本 | ~40 行 stdlib | ~150–200 行 stdlib |
| 重连 | **浏览器自动**（+ `Last-Event-ID`） | 手写 |
| 方向 | 单向（服务端→客户端） | 双向 |
| 我们的需要 | 推送日志/状态（**单向足够**）；触发走 POST | 仅"低延迟双向"才需要 |
| 结论 | **M1–M3 用 SSE**；WS 留 M4 可选 | |

## 18. pyserial 可选依赖与优雅降级详设（D1）

### 18.1 分层原则

**"可选"必须体现在三层，缺一层就会退化失败**：

| 层 | 要求 |
|---|---|
| **导入层** | 禁止顶层 `import serial`；必须懒加载 + 捕获 `ImportError` |
| **能力层** | 后端启动时探测 → `GET /api/capabilities` 返回 `{"serial": {"available": bool, "reason": str, "impl": "pyserial"\|"ctypes"\|null}}` |
| **视图层** | 前端据能力**先渲染再决定**：不可用时串口 Tab **禁用 + 给安装提示**，其余功能**完全不受影响** |

### 18.2 代码形态

```python
# services/elab/serial_backend/__init__.py
from __future__ import annotations
from typing import Protocol

class SerialBackend(Protocol):
    def list_ports(self) -> list[PortInfo]: ...
    def open(self, port: str, baud: int) -> Handle: ...

_backends: list[tuple[str, callable]] = []      # 有序：先注册先试

def register(name: str, factory): ...

def probe() -> tuple[SerialBackend | None, dict]:
    """返回 (后端, 能力描述)。任何异常都必须转成 reason，不得抛出。"""
    reasons = []
    for name, factory in _backends:
        try:
            return factory(), {"available": True, "impl": name}
        except Exception as exc:                # ImportError / OSError / ...
            reasons.append(f"{name}: {exc}")
    return None, {"available": False, "impl": None,
                  "reason": "; ".join(reasons),
                  "hint": "pip install pyserial"}
```

```python
# serial_backend/pyserial_backend.py  —— 只有这个文件 import serial
def factory():
    import serial                               # ★ 懒加载，顶层绝不 import
    from serial.tools import list_ports
    ...
```

### 18.3 降级阶梯

| 层级 | 条件 | 能力 |
|---|---|---|
| L0 完整 | pyserial 可用 | 枚举 + 读 + 写 + 波特率切换 + 断线重连 |
| L1 只读 | 仅 stdlib ctypes 后端可用（可选实现） | 枚举 + 读（**无写**）；UI 标注"降级" |
| L2 不可用 | 都没有 | 串口 Tab **禁用**；显示 `pip install pyserial`；`monitor` 步骤标 `inconclusive`（**不是 failed**） |

> L1 是否实现取决于后续精力；**L0/L2 必须做**，L1 是"零依赖洁癖"的备胎。

### 18.4 安装与分发

- 新增 `requirements-optional.txt`（只一行 `pyserial>=3.5`），**不**进 CI 的 `host-gate` 依赖。
- 驾驶舱启动时若串口不可用，日志与 UI 给**同一条**提示（避免两处文案不一致）。
- `elab doctor` 增一条信息级检查：`serial.pyserial`（有/无），**不影响 exit code**。

### 18.5 蓝牙口识别（G6/K5）

本机实测：`HKLM\HARDWARE\DEVICEMAP\SERIALCOMM` → **COM3–COM8 全部是 `\Device\BthModem*`**。

```python
BT_PREFIX = r"\Device\BthModem"
def list_ports_win():
    return [PortInfo(port=com, is_bluetooth=dev.startswith(BT_PREFIX))
            for dev, com in _read_serialcomm()]   # winreg
```

**自动选口规则**：

| 情形 | 行为 |
|---|---|
| `serial.default` 是具体口（如 `COM9`） | 直接用；不在则报错（**不静默改口**） |
| `auto` 且**唯一** USB 口 | 自动选它 |
| `auto` 且**多个** USB 口 | **不猜** → UI 让用户选（下拉 USB 优先、蓝牙置底并标注） |
| `auto` 且**只有蓝牙口** | 视为**无可用串口** → `inconclusive` + 提示"未检测到 USB 串口（COM3–8 为蓝牙虚拟口）" |

> 这条规则直接来自本机探测结果 —— 不做的话，驾驶舱会在你这台机器上**一上来就选中蓝牙口**，然后读到一片空白。

## 19. 一键适配工程（"适配"而非"改造"）—— 新增需求讨论

> 需求原文：*"我想在 UI 上实现一键适配工程的功能（即让 agent 调用专用 skill 对原生成的 at32 或者 stm32 进行 elab-flow 的专属平台化改造）。就是我从图形化配置的程序生成一个 cmake 模版程序，然后 elab-flow 能够进行一键适配接入。"*

### 19.1 结论先行：可以做，但**产品定义要改一个字**

把需求里的"**改造**"换成"**适配**"，这个功能的性质就从"有风险的重写"变成"可验证的取证"：

| | 「平台化改造」（原措辞） | 「一键适配」（建议） |
|---|---|---|
| 产出物 | 改动业务工程的 CMakeLists / 目录结构 | **一个 `projects/<name>.yaml`**（可能 + 一个 `chips/<vendor>/<id>.yaml`） |
| 业务工程 | 被修改 | **一个字节不动** |
| 验收 | 无客观标准 | **`guard.untouched == true` + `doctor --deep` 全绿 + `build` 产出 `.elf`** |
| 出问题 | 工程已被改坏 | 删掉那个 YAML 即可，无残留 |

**理由（这是本仓库最核心的资产）**：elab-Flow 的全部架构 —— 两个 `-D` 支点（`CMAKE_TOOLCHAIN_FILE` + `CMAKE_PROJECT_INCLUDE`）、外骨骼原则、零改动快照 —— 存在的唯一意义就是**不必改工程**。
如果"一键适配"去改工程，等于亲手把这个项目最值钱的卖点拆掉，而且**改完就再也无法证明零改动了**。

> ✅ 所以：**一键适配 = 一键探测 + 生成声明文件 + 自动验收**。这也是它最容易做、最安全、最可复现的形态。

### 19.2 为什么可行：生成器产物是"机器生成的、高度规整的"

AT32 WorkBench / STM32CubeMX 导出的 CMake 工程有**稳定的结构指纹**（下面是本仓库两个真实工程的实测值，不是推测）：

| 事实（要探测的东西） | 探测方法 | AT32_TEST（B 类） | STM32_TEST（A 类） |
|---|---|---|---|
| **厂商 / 生成器** | `CMakeLists.txt` 里的 `add_subdirectory(cmake/<dir>)` | `cmake/at32_workbench` | `cmake/stm32cubemx` |
| 同上（第二指纹） | `cmake/<dir>/CMakeLists.txt` 里的变量名 | `WK_Defines_Syms` | `MX_Defines_Syms` |
| **芯片编译宏** | `cmake/<dir>/CMakeLists.txt` 的 define 列表 | `AT32F421G8U7` | `STM32F103xB` |
| **工程名 / 产物名** | `set(CMAKE_PROJECT_NAME X)`，回退 `project(X)` | `TEST` | `TEST` |
| **archetype** | `CMakeLists.txt` 内是否有**行内 `include()` 工具链** | **有** → A/B 判 **B** | **无** → 判 **A** |
| 同上（第二指纹，连到约束 C1） | 工具链 cmake 用的**链接变量名** | `CMAKE_C_LINK_FLAGS` | `CMAKE_EXE_LINKER_FLAGS` |
| **链接脚本** | 工具链 cmake 的 `-T "…/<x>.ld"` | `AT32F421x8_FLASH.ld` | `STM32F103XX_FLASH.ld` |
| **内存布局** | ld 的 `MEMORY` 段 | 64K/16K | 64K(ld)/20K |
| 生成器原始工程文件 | `*.ATWP` / `*.ioc` / `.mxproject` | `template.ATWP` | `TEST.ioc` |
| 工具链候选数 | `cmake/*.cmake` 里的 `CMAKE_C_COMPILER` 文件 | 1 个 | **2 个**（还有 `starm-clang.cmake`） |

**关键**：`cmake/<vendor_dir>/CMakeLists.txt` 第 7 行左右那个 define（`AT32F421G8U7` / `STM32F103xB`）**就是真正送进编译器的宏** —— 它是芯片识别的最权威源。而 `cmake/at32_workbench` / `cmake/stm32cubemx` 这个目录名，是**厂商生成的铁证**（手写工程不会这么命名）。

### 19.3 证据分级：为什么不能"读一个文件就把结论定了"（★ 有实证反例）

本项目里已经出现**同一工程内部多个元数据文件互相矛盾**的真实现象：

| 文件 | 声明的芯片 | 包 | 状态 |
|---|---|---|---|
| `cmake/at32_workbench/CMakeLists.txt` | `AT32F421G8U7` | — | ✅ **编译事实** |
| `.vscode/at32_chip.json` | `AT32F421G8U7` | `QFN28` | ✅ 与编译事实一致 |
| `template.ATWP` | **`AT32F421C8T7`** | **`LQFP48`** | ❌ **与编译事实不符 → 已证伪** |

`template.ATWP` 是生成器留下的模板文件，**它过期了**。如果探测器图省事去读 `.ATWP`，就会把工程适配成错误的型号。

由此定下**证据分级**（冲突时高者胜，低者的异议写进 `conflicts[]` 上报）：

| 级别 | 来源 | 可靠性 | 实测样本 |
|---|---|---|---|
| **E1 编译事实** | `cmake/<vendor>/CMakeLists.txt` 的 defines；`compile_commands.json`（需先 configure） | ★★★★★ | `AT32F421G8U7` / `STM32F103xB` |
| **E2 生成器结构化元数据** | `.vscode/at32_chip.json`；`*.ioc` 的 `Mcu.CPN` | ★★★★ | `{"chip":"AT32F421G8U7","sram":"16KB"}` |
| **E3 链接事实** | ld 的 `MEMORY`；工具链 cmake 的 `-T` 行 | ★★★★（**内存布局的唯一权威**） | STM32 ld 只给 64K ≠ 官方 128K → **以 ld 为准** |
| **E4 结构约定** | `add_subdirectory(cmake/<vendor>)`、`WK_/MX_Defines_Syms`、工具链文件名 | ★★★★（判**厂商**最可靠） | `at32_workbench` vs `stm32cubemx` |
| **E5 生成器模板文件** | `template.ATWP` | ★★ **可能过期** | ❌ **已实证反例** |
| **E6 文件名猜测** | 目录名里猜芯片 | ★ 仅作提示 | — |

> ★ 这条分级不是洁癖：**这个仓库里已经有一个文件的结论是错的**。适配器必须自带冲突检测，否则会把错误静默写进 `projects/*.yaml`。

### 19.4 适配的三个档位（明确边界，避免"这也不行"式的模糊）

| 档 | 前提条件 | 产出 | 业务工程 | 覆盖度 |
|---|---|---|---|---|
| **T1 零改动适配** | 工程有 CMakeLists + 工具链 cmake + `.ld`（**= 用户在图形配置器里选 CMake 工具链导出的标准产物**） | `projects/<name>.yaml` | **不动** | ★ 需求原文描述的主场景 |
| **T2 桥接适配** | 工程有 CMakeLists，但结构别扭（如产物名不可控、需额外 `add_compile_options`） | `projects/<name>.yaml` + **`bridges/<name>/CMakeLists.txt`（放在 elab-flow 侧！）** | **仍不动** | 少数工程 |
| **T3 需要真改造** | 工程**根本没有 CMake**（Keil / IAR / Makefile 工程） | ❌ 不做，**明确提示**："请在 AT32 WorkBench / CubeMX 里把工具链切到 CMake 后重新导出" | 不动 | 前置条件不满足 |

**T2 的桥接思路**（值得单独说）：`projects/*.yaml` 的 `build.source` 指向哪个 CMakeLists 是我们自己定的。所以可以让它指向 **elab-flow 内部的一个桥接文件**：

```cmake
# bridges/<name>/CMakeLists.txt —— 住在 elab-flow 里，绝不放进业务工程
cmake_minimum_required(VERSION 3.22)
project(elab_bridge C ASM)
add_subdirectory("${ELAB_TARGET_ROOT}" "${CMAKE_BINARY_DIR}/target")
```

于是连"结构别扭"的工程也能做到 **`guard.untouched == true`**。这是"不改器官"原则的一个漂亮应用。

> ⚠️ **T3 的边界必须写进 UI 文案**：用户真正需要知道的是 —— *"我在图形配置器里必须选 CMake 工具链"*，而不是 *"elab 适配失败了"*。这是**输入前提**，不是缺陷。

### 19.5 ★ agent/skill 与确定性工具的职责边界（本方案最重要的建议）

需求说"**让 agent 调用专用 skill**"。这个方向完全支持，但**不能让 agent 承担取证工作**，否则"一键适配"会变成"每次结果不一样" —— 那就正面违背了这个仓库的根本承诺（可复现、可校验、证据链）。

| 环节 | 由谁做 | 为什么 |
|---|---|---|
| 读 CMakeLists / Presets / `cmake/<vendor>/*` / `.ld` | **确定性探测器** `elab adapt --probe --json` | 有唯一正确答案，不该由模型"判断" |
| 芯片匹配到 `chips/*.yaml` | 确定性（define ↔ `compiler_defines` / `part` 匹配） | 同上 |
| 多源冲突裁决 | 确定性优先级链（§19.3 E1…E6），冲突写入 `conflicts[]` | 可复现 |
| 生成 `projects/*.yaml` | 确定性模板渲染（**照 `skillgen.py` 的既有做法**） | 已有先例：`elab skill` 就是"从数据渲染，不手写" |
| **`conflicts[]` 非空** → 裁决 | **agent + skill** | 需要判断，且应**向用户提问而非猜** |
| **找不到匹配芯片** → 纳新芯片 | **agent + skill**（渲染 `chips/*.yaml` 草案 + 人工确认频率/内存） | 需要判断 |
| 多个 `.ld` 候选 / 多个工具链候选 | **agent + skill**（提问） | 需要判断 |
| **验收** | **确定性**：`doctor --deep` + `build` + `guard.untouched` | 已是现成的 oracle，见 §19.6 |

> **一句话**：**探测器负责取证，skill 负责在证据不足时提问。**
> 这与本项目既有的 `elab skill`（从 `chips/*.yaml` 渲染 SKILL.md）是同一条思路的延伸 —— skill 的内容**不手写**。

**由此得到两个交付物**：

1. `elab adapt <path>`（新增子命令，确定性）—— 探测 + 生成 + `--check` 幂等校验；
2. `elab skill --adapt`（扩展 `skillgen.py`）—— 渲染一份**"适配流程 skill"**，告诉 agent：按什么顺序取证、冲突时问什么、验收看哪三个绿灯。

**"一键"的深意**：`elab adapt` 单独可用（不依赖 agent、可进 CI、可复现），skill 只是在 `conflicts` 出现时才出场。这就是**优雅降级**：LLM 挂了，适配仍然能做。

### 19.6 验收 oracle 是现成的（这是本功能最优雅的地方）

"适配成功"的定义**不需要新造任何机制**，它正好是仓库里已有的三个断言：

| 断言 | 已有实现 | 含义 |
|---|---|---|
| `elab doctor -p <name> --deep` 全绿 | `doctor.py`（真跑 configure 取证） | YAML 里的芯片参数与**实际编译命令**一致，无两源漂移 |
| `elab build -p <name>` 产出 `.elf` | `builder.py`（含 A 类 `.elf` 后缀约定 C5） | 工具链接管成功、产物名正确 |
| **`guard.untouched == true`** | `builder.py` 文件树快照（约束 C4/C10） | **业务工程一个字节都没动** ← 这条是"适配"区别于"改造"的**客观证据** |

> ★ 第三条是本功能的说服力所在：它把"我没改你的代码"从**承诺**变成了**可断言的结果**。

### 19.7 生成的 `projects/*.yaml` 自带 `provenance`（证据链落在产物里）

现有 `projects/at32_test.yaml` 是手写的、注释详实。生成的版本会薄一些，所以**必须自带出处**，否则三个月后没人知道 `archetype: B` 是凭什么判的：

### 19.9 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| A1 | **用户手改过生成工程**（半手工），规则失效 | 探测器输出 `confidence`；任何一级证据缺失或冲突 → **强制人工确认，绝不静默写** |
| A2 | **按行号匹配会碎**（★ 现存隐患） | `chips/*.yaml` 的 pitfalls 里写着"CMakeLists **第 22 行** `include(...)`" —— **行号是脆弱的**（STM32 那行在第 38/39 行）。适配器一律**按特征匹配**（正则 + 上下文），不按行号；建议顺手把 pitfalls 的措辞也改成按特征描述 |
| A3 | 多个 `.ld` 候选（FLASH / RAM / 多个型号） | 默认 `*FLASH*.ld`；多命中 → 提问 |
| A4 | 多个工具链候选 | STM32_TEST 实测有 `gcc-arm-none-eabi.cmake` **和** `starm-clang.cmake`。规则：**以 `CMakePresets.json` 的 `toolchainFile` 指定的那个为准**；无 preset → 提问 |
| A5 | 同名 `projects/*.yaml` 已存在 | 默认 `--check` 只校验不覆盖；`--force` 才覆盖；覆盖前备份 |
| A6 | 工程在仓库外（绝对路径） | 已支持（`root:` 可绝对）；注意 Windows 反斜杠 → 走 `config.to_fwd()` |
| A7 | 生成的 YAML 被用户手改后又被 adapt 覆盖 | 生成时打 `generated-by` 头；检测到该头被删 → 视为"人工接管"，adapt 只提示不覆盖 |
| A8 | **幂等性** | `elab adapt <path> --check` 对已适配工程应 **no-op 且 exit 0**（用户明确重视幂等） |
| A9 | 新芯片（`chips/*.yaml` 里没有） | 升级为"适配工程 + 纳新芯片"：渲染 chip yaml 草案（内存取自 ld、频率标 `TODO`）→ 人工确认；确认后 `elab skill` 自动补出 per-chip skill |
| A10 | 芯片型号别名（`STM32F103C8T6` vs `STM32F103xB`） | 用**编译宏**做匹配键（宏天生是"族级"），CPN 只作提示；匹配不到时提问 |

### 20.2 被迫做的几个判断（都有理由，不是随手的）

| # | 判断 | 反面代价 |
|---|---|---|
| 1 | **不用 `<StrictMode>`** | React 18 开发模式会"挂载→卸载→再挂载"，SSE 会开两条连接 → **事件被重复归约、日志翻倍**。这个假 bug 只在 `npm run dev` 出现，会白吃排查时间。清理正确性由 `sse.close()` / LogView 的 cleanup 保证 |
| 2 | **宽度走 CSS 变量而非行内 `width`** | 行内优先级最高，会压过窄屏媒体查询 → 响应式降级直接失效（`AppFrame.module.css`） |
| 3 | **`dist/` 文件名不带内容哈希** | 带哈希会让每次改动产生"新增+删除"噪声；不带哈希时"改了 tsx 没重新 build"恰好表现为**一份 diff**，正是守卫要的信号（§15.6） |
| 4 | **日志计数改增量累加** | 原先每帧 `snapshot()` 全扫：4000 行 × 3 Tab × 60fps ≈ 72 万次/秒。改为 `push` 时累加、裁剪时扣减（`logs.ts` 的 `stats`） |
| 5 | **DOM 行数封顶 1500（缓冲 4000）** | 环形缓冲只管内存、不管 DOM 节点。触顶后**从头部逐行摘除**（O(掉队行数)），而不是整体重建（O(1500)） |
| 6 | **只用 SSE 一条路（不区分历史/实时）** | 服务端 `_sse()` 本就是"先重放存量、再跟读活队列"，历史 run 走重放分支并以 `stream/closed(run-finished)` 收尾。前端不再分叉 → 少一类竞态。代价：历史 run 的 `proc/*` 是逐条帧（不走 100ms 合并） |
| 7 | **`markStreamClosed()` 兜底** | 正常路径 `run/end` 一定先于 `stream/closed` 到达。万一缺失（硬杀/写盘失败），界面会**永远显示"运行中"**且取消键永远亮着。宁可显式判失败 |
| 8 | **`doctor` 归入「构建」Tab（证据轨仍只三 Tab）** | 流水线五步（doctor/build/flash/debug_verify/monitor）与方案 §5.4 定的三 Tab 不是一一对应，故 `tabOfEvent` 里有一条**显式兜底**：`flash`/`debug_verify`→烧录、`monitor`→串口、**其余（含 `doctor`）→构建**。体检与编译都是宿主侧、纯文本、不碰硬件的步骤，共用一个"宿主侧输出"面板比单开第四个 Tab 更贴方案。代价：构建 Tab 的徽标行数**包含体检输出**（`构建 36` 里 28 行是体检） |

三点值得记下来：

### 20.4 本轮联调发现的缺陷（已修）

> 错的只是"没有把 seq 告诉浏览器"。它和 §6.1 里那次"分块/裸写"事故同源：
> **SSE 的正确性取决于协议帧头（`id:` / chunked 长度）是否正确，而这些恰好都不体现在业务日志里。**

关于 `serial/closed-loop`，有两条**设计约束**值得记下来，它们决定了它只能这么接：

1. **`monitor.py` 不许 import `kernel.events`**。它是纯库（`judge()` 是纯函数，可离线单测三态），
   一旦让它认识事件，就把"判定"与"传输"焊死了。故用**回调**把"串口发生了什么"交出去，
   接线放在 `run.py`（那个 run 的**唯一写者**）里 —— 单写者模型不破。
2. **`rule`/`evidence` 必须从 `judge()` 已算好的 `evidence[0]` 取，不许解析 `reason` 文案**。
   `evidence[0]` 本来就带 `rule`/`line` 键（`monitor.py:178,189,201,212`）；
   而 `reason` 是中文字符串，文案一改就**静默**取到空串 —— 这正是本仓库反复踩的"静默失效"形态。

设计要点（对应约束 C27）：

1. **无状态往返**（open → write → read → close），**不做常驻会话**。串口是独占资源：
   常驻会话会与 `elab run` 的 monitor 互斥，且持口线程一旦僵死就**没人释放** ——
   只能重启整个驾驶舱。无状态把占用压进**一次请求**，**天然与 monitor 串行**；
   代价是每次重开（几十 ms）。
2. **写权限必须显式**：`SerialIO(..., for_write=True)` 才申请 `GENERIC_WRITE`，只读实例调
   `write()` 直接 `raise`。理由是 pyserial 后端**天然可写** —— 不加这道闸门，"只读"
   就只是个口号，一次笔误就能把数据发给固件。
3. **跨进程互斥要提前拦**：`flash`/`debug_verify`/`monitor` 任一在跑 → **409** 且**指名道姓**
   报出是哪个 run。否则用户只会看到 `ERROR_ACCESS_DENIED`（N5），然后去拔插、去杀进程 ——
   真正的原因（自己刚点的闭环占着）永远查不到。
4. **`ok:false` 也是 200**（400/409 除外，那是"请求不合法"/"被占"）：失败与成功要渲染的
   字段完全一样（`port`/`baud`/`error`），用 5xx 只会让前端走异常分支、丢掉结构化信息。
5. **空输入要在加行结束符之前判定**：`""` 若在加 `CRLF` 之后才判空，会变成 `b"\r\n"`
   被当成有效载荷发出去 —— 一个"空回车"照样能打断固件的行解析器（**离线用例已回归**）。

设计要点（对应约束 C28）：

1. **落盘回调由调用方注入**（`roundtrip(journal=…)`）：`serialterm` 只管"发一条、收一段"，
   **不认识文件与路径**。CLI 与驾驶舱指向同一份留档，"这块板子上发生过什么"只有一处记录。
2. **记录从结果生成，不在往返内部插桩**（`_journal(res)`）：无论从哪条早退路径返回，
   都**恰好**落一对 (TX, RX*) —— 不会漏，也不会因为将来多一条 `return` 就少记一笔；
   失败路径同样落一条 `tx(ok:false)`，"我敲过这一行"不因失败而消失。
3. **滚动按文件大小触发**（`stat()` O(1)），**绝不**每次 append 数行数 —— CLI 与驾驶舱
   是两个进程，行数计数在跨进程下必然漂移。重写只留尾部 N 条 + `os.replace` 原子替换，
   断电/并发下也不会留半截文件。
4. **`count()` 数行、`tail()` 给可解析的**：两者之差是"有多少行读坏了"的**唯一**观测窗口，
   刻意不抹平。留档不是 state（约束 C28），一行坏掉不该让整段历史不可读，但也不许静默。
5. **界面回填的时机是"清空本地缓冲之后、挂 SSE 之前"**，而不是"进串口 Tab 时"：
   `LogView` 是纯追加渲染，没有"插历史到顶部"的能力；在清空后立刻回填，
   顺序天然正确（留档在前、实时在后），否则就是**时间倒错**。
   回填失败**静默**：留档是锦上添花，串口能用才是要紧事。

**M5.6（UI 一键适配）设计要点**：

1. **两段式，probe 永远在前**：`action:"probe"`（只读）→ `action:"write"`（落盘）。
   "落不落盘"必须是用户看得见的独立动作 —— 与 `/api/plan`（GET 纯读）→ `/api/run`
   （POST 真跑）的动词纪律同一条。
2. **`tier:"T3"` 是数据不是错误**（200 携带）：它要渲染成"需要真改造"的说明；
   只有**请求不合法**（相对路径/目录不存在/未知 action）才 400。
3. **三绿灯 verify 刻意不在 HTTP 里同步做**：真跑 configure + 编译是十几秒级，
   同步做会把服务线程钉死（§5.1 K1 的反面教材）。故返回 `next.steps = [doctor_deep, build]`
   引导前端走**现有** run 通道 —— 判据（doctor_deep 全绿 / 出 elf / guard.untouched）
   一个不少，且进度走 SSE、结果落事件流。
4. **写入必须热重载 Config**（★ 真浏览器验收抓出的真缺陷）：服务进程的 `Config`
   在启动时固化，适配写出的新 `projects/<name>.yaml` 对它不可见 —— 症状是
   "写入成功、卡片却永远不出现、`/api/run` 也起不了新工程"，比报错更迷惑。
   CLI 的 `_adapt_verify` 早有"写入后重载"的对应逻辑，服务端漏了同款。
   修法：`written` 为真时新建 `Config(root)` 并替换 handler 类属性与 `mgr.cfg`
   （赋值原子；在途请求仍握旧引用跑完，旧配置对旧工程自洽）。
5. **前端复用而非复刻**：面板只管"收集路径 → 展示探测结果 → 触发写入"，
   tier/置信度/芯片/证据链全部来自后端探测的纯数据；新名可改（默认目录名推导），
   写入成功后由 App 收尾（刷新目录 + 选中新工程），不重复实现任何探测逻辑。

**单步独立按钮 + 「跑全闭环」显式步序（约束 C30）**：

用户实测反馈两条：① "单步执行应该做到具体的编译或者烧录或者串口监视界面，界面内的独立按钮"；
② "点击全闭环执行后，跑完编译就自动结束了"。

1. **「跑全闭环」的根因**：`onRunAll` 不带 steps → `POST /api/run` 走后端
   `DEFAULT_STEPS = doctor + build`（那是 M1 验收范围的"默认两步"）。按钮 title 承诺
   "全量步序（含上板）"，实际只跑两步 —— 行为与承诺**静默背离**。
   修在**前端**（`StageRail.fullLoopSteps()`：全部步骤 − `doctor_deep` − 按
   `card.steps[id].ok` 过滤不可用项），不改后端默认：CLI/API 的轻量默认是对的
   （点一下看看不必烧板），错的是 UI 把自己的语义寄托在别人的默认值上。
   ★ **空闲骨架与按钮同源**（同一个 `fullLoopSteps()` 画状态带）—— 否则
   "骨架画五步、点下去跑两步"的自相矛盾会直接暴露给用户。
2. **单步 = 独立按钮，且放在"干这件事的界面"里**：阶段轨「单步」下拉取消，
   改为一排六颗（体检/深度体检/编译/烧录/调试校验/串口闭环），可用性来自服务端
   `card.steps[id].ok`、置灰时 tooltip 直接说原因；证据轨按 Tab 放对应按钮：
   构建→「编译」、烧录→「烧录/调试校验」、串口→「串口闭环」。两处按钮共用
   同一份可用性数据，置灰理由永远一致。

**验收（真浏览器 + 路由拦截，不真烧板）**：

```text
① 拦截 POST /api/run → 点「跑全闭环」（选中 at32_test）
   请求体 steps = ["doctor","build","flash","debug_verify"]
   （at32_test 未声明 monitor.close_on → monitor 被可用性过滤正确排除）
② 阶段轨「单步」组 aria-label="单步执行"，六颗按钮齐全；
   at32_test 下「串口闭环」置灰（reason：未声明 close_on）
③ 证据轨：构建 Tab 出「编译」、烧录 Tab 出「烧录/调试校验」、串口 Tab 出「串口闭环」
④ 单步「烧录」按钮真机实测：run r-c61be04b（at32_test, steps=[flash]）→ status ok
```

**串口 Tab 的常驻监视（serialmon + 约束 C31）**：

用户实测反馈："串口里面这一步不对，应该是：打开串口监视和关闭监视"。
—— 串口 Tab 里放的应该是**常驻监视**（人要看设备实时输出），不是「串口闭环」
（那是判定，阶段轨已有）。M3-b 曾裁定"不做常驻会话"，其依据（N5：串口独占、
持口线程僵死没人释放）至今成立 —— 所以 `services/elab/serialmon.py` 带三道防身：

1. **单例 + 一键显式关闭**：进程内只有一个会话（串口独占，本就该只有一个）；
   按钮关闭/重复关闭幂等；重复打开指名道姓（"监视已在进行 COM10@115200"）。
2. **读线程异常自愈**：`read` 阻塞上限 200ms、循环查 stop 事件；任何异常
   （拔线/口被抢/驱动报错）→ 记入 `error`、`alive=False` 自动收摊 ——
   **绝不带着死口挂着**（这正是 M3-b 反对常驻的核心理由，必须拆掉）。
3. **写通道路由进会话**：监视开着时 `POST /api/serial` 不再重开口，直接写进
   已打开的口（`via:"monitor"`）；回显不再由请求带回 —— 读线程会把它送进
   实时流。TX 照旧落 console 留档（"我敲过这一行"不因失败消失，M3-b2 语义保留）。

输出走哪条道（C31 后半句）：**不进 run 事件流**（不属于任何 run，C17 单写者）、
**不落 console 留档**（留档是"我敲过什么"的 TX/RX 历史，监视输出是设备喋喋不休的
心跳，落盘只会撑爆它）—— 只活在服务端环形缓冲（2000 行 + `seq` 增量游标 +
`gap` 丢行显式报告 + 残留半行 1s 冲刷）与浏览器本地缓冲，前端 600ms 轮询
`GET /api/serial/monitor?after=N`。它是"看"，不是"证据"；要证据走闭环 monitor 步骤。

互斥双向闭环（约束 N5 的驾驶舱侧守卫，两边都 409 指名道姓）：
监视开着 → 起含 flash/debug_verify/monitor 的闭环被拒（"先关闭监视"）；
闭环在跑 → 打开监视被拒（"等它跑完或先取消"）。

★ **实现坑（真机首测即抓出）**：读线程绝不能用 `with self.io` —— `SerialIO.__enter__`
会**二次 open 同一个口**，第二次 `CreateFileW` 撞上自己持有的独占句柄 →
`ERROR_ACCESS_DENIED`，会话刚打开就被自己的异常自愈收掉。open 与线程启动的
时序必须是"start() 里 open 一次，线程只读不重开，收口统一在 shutdown()"。

**真机验收（at32f421g8u7，板子在跑带心跳的固件）**：

```text
POST /api/serial/monitor {action:open, project:at32f421g8u7}
  → 200 ok:true COM10@115200（ctypes）
GET ?after=0（3s 后）→ seq=4，lines=[alive] tick=1124..1127（每秒一行，实时流入）
GET ?after=4（1.5s 后）→ seq 5..20 共 16 行，gap=0（增量游标正确）
POST /api/serial {data:"status"} → 200 via:"monitor" written:8B（路由进会话，未重开口）
POST /api/run {steps:[monitor]} → 409 "串口监视正占用 COM10 —— 先在串口 Tab 点「关闭监视」"
POST {action:close} → ok，closed.lines=35
```

### 20.6 第二轮：把"看不见的丢事件"变成能测的量

N7~N12 有一个共同点：**服务端全对、HTTP 全 200、`seq` 全单调、日志无一行报错**，
错的只在"帧头/白名单/判据"这类**协议边角**。尤其是 N12 —— 它把
"浏览器到底收到了哪些事件"变成了唯一的突破口。

所以本轮补了一件事：给前端加一个**常驻、只读、无副作用**的自测钩子
（`cockpit/web/src/events/sse.ts`）：

```js
window.__elab.ingest()   // → { "proc/stdout": 32, "proc/stdout-batch": 8, "run/end": 2, ... }
window.__elab.logs       // → LogBook：counts() / for(tab).snapshot()
```

理由：驾驶舱的产物入库、运行时零 Node，**没有 Node 侧测试运行器**，
"事件有没有到浏览器"这个最基本的问题此前完全不可观测。有了它，一次
`page.evaluate` 就能拿到判定 N12 的关键证据（修复前 `proc/stdout-batch` 计数为
**0**、`proc/stdout` 停在上一次重放的 32 条不动；修复后合并帧计数 8、
环形缓冲随 run 实时涨到 36）。

**修复后的一次完整验收（真浏览器、走界面按钮「跑全闭环」）**：

| 判据 | 实测 |
|---|---|
| 日志是否**实时**滚动 | 运行途中行数持续增长，峰值 = 最终值 = **36**（而不是跑完才一次性出现） |
| 状态带 | `ok`（体检 0.23s / 编译 5.88s） |
| 徽标 / 元信息 / DOM 行数 | `构建 36` / `36 行` / `36` —— **三者一致**（此前是 3 / 3 / 36） |
| 空态覆盖层 | `emptyCount = 0`（N10） |
| 内存占位 | FLASH 7.39% / 4.73 KB · RAM 9.62% / 1.54 KB · **数据取自 .map** |
| 产物 | ELF 156.8 KB / HEX 13.4 KB / BIN 4.7 KB / **MAP**（N6 在界面上可见） |
| 布局 / 报错 | 3 列、无横向滚动、**页面与控制台零报错** |

> 这一轮真正的教训不是某一条 bug，而是**验证手段本身要能观测"协议边角"**。
> 前面之所以能在 N11/N12 上兜圈子，正是因为"服务端一切正常"被误当成了
> "链路正常"——而 SSE 的正确性恰恰全在帧头与订阅关系上，它们**不体现在业务日志里**。

### 21.8 中列吃满（2026-10-08 晚二连：用户"中间间隔还是很大"）

修法一行：`.center > * { flex: 1 1 auto; width: 100%; min-width: 0; }`。
证据轨无此问题（在纵向 flex 的 aside 里，交叉轴自动 stretch）。
实测（verify_ui8.cjs）：展开/收起两态 gap 均为 0（690px/938px 满宽），无 pageerror。
