# 干跑验证报告：AT32_TEST 接入 elab-Flow

> 目的：不做 CLI，只用**三个数据文件 + 两个工具链脚本**，真跑一次 cmake，
> 验证"业务代码零改动 + 跨芯片编译工作链"这个核心假设是否成立。
> 结论：**成立**，但暴露了 3 个必须写进架构的约束（其中 1 个只在真跑时才暴露）。

## 2. V1 结果：只用工具链文件 —— **不够**

### ✓ 成功的部分：编译器被锁定

CMake 在工具链阶段锁定 `CMAKE_C_COMPILER`，工程内第 22 行
`set(CMAKE_C_COMPILER ${TOOLCHAIN_PREFIX}gcc)`（裸名）**被忽略**。
实际编译命令用的是绝对路径：

```
C:\DevEnv\GNU-tools-for-STM32\bin\arm-none-eabi-gcc.exe ...
```

→ **这是好消息**：elab 能可靠 pin 住工具链版本（"不依赖主机 PATH"成立）。

### ✗ 问题 1：编译 flags 被工程自带工具链完全覆盖

实际生效的 `CMAKE_C_FLAGS` = AT32 工程的值，**elab 的值被替换掉了**。证据：

| 来源 | 期望 | 实际 |
|---|---|---|
| elab `gcc.cmake` | `-mcpu=cortex-m4 -mfloat-abi=soft ... -std=gnu11` | 被覆盖 |
| AT32 `gcc-arm-none-eabi.cmake` | `-mcpu=cortex-m4 -mfloat-abi=soft -ffunction-sections -fdata-sections -Wall -Wextra` | **生效** |
| `-std=gnu11` 真正来源 | — | 工程的 `CMAKE_C_STANDARD 11` + `CMAKE_C_EXTENSIONS ON`，**不是** elab |

### ✗ 问题 2（最危险）：链接参数**双重叠加**

V1 的链接行：

```
LINK_FLAGS = -mcpu=... -mfloat-abi=soft -T "...AT32F421x8_FLASH.ld" -Wl,--gc-sections
             -Wl,--print-memory-usage --specs=nano.specs          ← elab (CMAKE_EXE_LINKER_FLAGS)
             -Wl,-Map=TEST.map -Wl,--start-group -lc -lm -Wl,--end-group
             -mcpu=... -mfloat-abi=soft -T "...AT32F421x8_FLASH.ld" -Wl,--gc-sections
             -Wl,--print-memory-usage --specs=nano.specs          ← AT32 (CMAKE_C_LINK_FLAGS)
```

根因：**两个变量不同名**，CMake 把两份都拼进链接行。
- elab 用 `CMAKE_EXE_LINKER_FLAGS`
- AT32 工程用 `CMAKE_C_LINK_FLAGS`

> ⚠️ **当前只是冗余（两源恰好一致）**。一旦 `chip.yaml` 与工程参数不一致，
> 就会出现**两个不同的 `-T`，后者静默生效** —— 得到一个"参数自相矛盾"的固件，且不报错。
> **这类 bug 是最难查的一类。必须显式消除。**

## 3. V2 结果：加 `inject.cmake` 盖章 —— **成功**

### ✓ 链接参数恢复单份

`inject.cmake` 里显式清掉工程留下的那一份后：

```
LINK_FLAGS = -mcpu=cortex-m4 -mfloat-abi=soft -T "...AT32F421x8_FLASH.ld"
             -Wl,--gc-sections -Wl,--print-memory-usage --specs=nano.specs
```
`FLASH.ld` 出现次数：**1**（V1 是 2）。

### ✗ 问题 3：真跑才暴露的坑（纸上干跑绝不会发现）

第一次 V2 构建**失败**：

```
arm-none-eabi-gcc.exe: error: unrecognized -mcpu target: cortex-m4 -mfloat-abi=soft
```

根因：`add_compile_options(${_elab_flags})` 把整串当成**一个带引号的参数**传给 gcc。
修正为独立参数后通过：

```cmake
add_compile_options(-mcpu=${ELAB_CPU} -mfloat-abi=${ELAB_FPU})   # ✓
# add_compile_options(${_elab_flags})                            # ✗ 整串被引号包住
```

### ✓ 最终构建成功，内存占用与 chip.yaml 完全一致

```
[28/28] Linking C executable TEST.elf
Memory region   Used Size  Region Size  %age Used
     FLASH:        4840 B      64 KB      7.39%
       RAM:        1576 B      16 KB      9.62%
```

`arm-none-eabi-size`：`text 4828 / data 12 / bss 1572`

对照 `chips/artery/at32f421g8.yaml` 声明的 `flash: 0x10000 (64K)` / `ram: 0x4000 (16K)`
→ **完全吻合**，`verify.expect_memory` 校验会通过。

### ✓ 产物齐全

`TEST.elf` (159764 B)、`TEST.hex` (13709 B) 都落在 `.work/v2/`，
AT32 工程自带的 POST_BUILD `objcopy -O ihex` 正常触发。

## 5. 实验得出的 4 条架构约束（要写进设计）

| # | 约束 | 依据 |
|---|---|---|
| C1 | **B 类工程必须挂 `CMAKE_PROJECT_INCLUDE`**，且 `inject.cmake` 要同时：盖 flags、盖链接、**清掉 `CMAKE_C_LINK_FLAGS`** | V1 双重叠加 |
| C2 | `inject.cmake` 里 `add_compile_options` **必须拆成独立参数**，不能传整串 | V2 首次构建失败 |
| C3 | **`inject.cmake` 不盖 defines / include** —— B 类工程的 defines/include 由工程自己的 INTERFACE target 提供且是准确的，elab 再注入只会制造双源。`chip.yaml` 的 defines 降级为**仅供 `doctor` 校验** | V2 中 defines/include 全部来自工程且正确 |
| C4 | **`guard` 不能依赖 git**，要用文件树快照（路径+size+mtime） | AT32_TEST 非 git 仓库 |

### 附：一条重要的设计认识

对**自带 CMake 的工程（A/B/D 类）**，`chip.yaml` 的价值**不是"提供参数"**（工程里已经有），
而是三件事：
1. 提供**可校验的单一真相**（`verify.expect_*` 用来发现两源漂移）；
2. 提供**跨芯片一致性**（同一套 L2 能编所有芯片）；
3. 提供 **C 类工程（无 CMake）的兜底参数**。

→ 这直接决定了 `inject.cmake` 应该"只盖必要的（flags/链接），不盖冗余的（defines/include）"。
