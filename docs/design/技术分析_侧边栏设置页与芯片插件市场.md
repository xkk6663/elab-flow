# 技术分析：侧边栏「设置」内嵌芯片插件市场与适配包管理

> 状态：**调研 + 技术分析（未实施）**。日期：2026-10-31。
> 输入：Trae 分享《社区驱动插件化嵌入式开发平台》（M1/M2 已完成，M3 = 驾驶舱市场页）
> + 本仓现有 DSH 驾驶舱面板与内核 `/api/packs`。
> 用户诉求原话：**"加一个设置按键，点进设置后就是另外一个 UI 界面里面另外管理设备包和插件市场，
> 就可以不用全塞到一个界面里面"**。

---

## 0. 结论摘要

1. **可行，且不需要新造业务实现**：内核侧 `services/elab/pkg.py` 已把「市场索引 → 解析来源 →
   安装/卸载/校验/更新」全部实现，CLI `elab pkg ...` 是现成入口；驾驶舱只差一层
   **写动作 HTTP 面**（当前只有只读 `GET /api/packs`）。
2. **UI 形态推荐"面板内视图切换"**：在面板顶栏（工程条右侧）加一个 `⚙` 按钮，
   点击后整块面板切成"设置视图"（市场 / 已装包 / 内核设置三个分段页签），
   左上角 `← 返回` 回到闭环主视图。**不新增 DSH 槽位**，风险最低，也最贴合用户的"另一个界面"。
3. **必须补的内核缺口（3 个）**：
   - `POST /api/pkg/install|remove|verify|update`（写动作）；
   - 安装/卸载后**重载 Config**（否则新芯片对运行中的驾驶舱不可见）；
   - 市场读取与已装视图**拆开**（`GET /api/packs` 默认会在请求线程里同步拉远程索引，
     最长 15s 超时；设置页首屏应先用 `?market=0`，再显式刷新市场）。
4. **工具层改动是"薄壳"**：代理白名单加 5 个端点、`icd-client` 加 5 个方法、
   `CockpitPane` 加视图状态与按钮、新增 1~2 个纯展示组件；**不在插件里解析 `pack.yaml`、
   不读市场索引、不跑 git** —— 这些全部留在内核。

## 1. 背景与需求拆解

### 1.1 Trae 文章的落点

文章描述的 M1/M2 已经在本仓落地：`pack.yaml` schema、`packs/installed` 隔离安装、
内容哈希与安全审计、`requires` 握手、local/git/archive 三种来源、零服务器市场索引

`elab pkg search|install|bootstrap|list|remove|update|verify|index`、
内核只读投影 `GET /api/packs` + `capabilities.packs`。
文章结尾明确下一步是 **M3：驾驶舱市场页 UI（浏览 / 安装 / 卸载适配包）**——即本次需求。

### 1.2 需求拆成四条可验收项

| # | 需求 | 验收口径 |
|---|---|---|
| R1 | 面板里有一个「设置」入口 | 顶栏出现 `⚙`，点击后主视图被替换（不是弹窗、不是塞进同一屏） |

| R4 | 不与闭环主视图互相挤占 | 设置视图有独立返回入口；闭环运行状态在切回后仍是同一份 service 快照 |

## 2. 现状盘点：有什么、缺什么

### 2.1 内核（业务层）—— 业务实现已齐备，只缺 HTTP 写面

| 能力 | 位置 | 现状 |
|---|---|---|
| 包发现/状态投影 | `services/elab/pkg.py:754 status()` | ✅ 已装 + 市场条目（含 `installed` 布尔）一次返回 |
| 市场读取 | `pkg.py:574 load_market()` | ✅ HTTP 15s 超时 + `.work/pkg/market.json` 缓存 + 本仓索引兜底 |
| 搜索 | `pkg.py:656 search()` | ✅ 名称/厂商/平台/芯片/描述 模糊匹配 |
| 安装 | `pkg.py:447 install()` | ✅ 来源物化 + 清单校验 + 内容哈希强校验 + 复制后二次校验 + `.installed.json` |
| 官方包离线安装 | `pkg.py:499 bootstrap()` | ✅ `packs/official/**` 逐个安装 |
| 卸载 | `pkg.py:517 remove()` | ✅ 只允许删安装目录内的包 |
| 校验 | `pkg.py:534 verify()` | ✅ 清单/安全/哈希漂移 |
| 市场索引生成/校验 | `pkg.py:675 build_index()` / `:723 index_problems()` | ✅ `elab pkg index --check` |
| CLI 入口 | `services/elab/__main__.py:728 cmd_pkg()` | ✅ 全部子命令；安装后自动重生成平台 skill |
| HTTP 读 | `cockpit/server.py:852-856` | ✅ `GET /api/packs`（`?market=0` 跳过市场） |
| **HTTP 写** | — | ❌ **没有 install/remove/verify/update 端点** |
| **安装后热生效** | `cockpit/server.py:1150-1157`（`/api/adapt` write 后重建 Config） | ⚠️ 有先例，但 pkg 路径没有接上 |

> 关键实现细节：`Config` 对 `packs/chips` 是**实例级缓存**（`services/elab/config.py:55-57,81-118`）。
> 因此安装完成后必须重建 `Config` 并原子替换 `cfg` 与 `mgr.cfg`（与 `/api/adapt` 写入后的做法同源），
> 否则面板看不到新芯片、`/api/projects` 也不会出现引用新芯片的工程。

### 2.2 工具层（DSH 插件）—— 三处缺口

| 位置 | 现状 | 缺口 |

| `src/adapters/kernel-http/routes.ts:74-88` | `GET_ALLOW` / `POST_ALLOW` 方法白名单 | **无 `packs`、无 `pkg/*`** —— 客户端根本调不到内核包能力 |

## 3. 产品形态设计

### 3.1 三个候选方案与取舍

| 方案 | 做法 | 优点 | 风险/代价 |
|---|---|---|---|
| **A（推荐）面板内视图切换** | `CockpitPane` 内加 `view: 'work' \| 'settings'`；顶栏 `⚙` 进入，设置视图含"市场 / 已装 / 内核设置"分段；`← 返回` 回主视图 | 改动集中在一个组件；复用同一 `sessionId`/host；不碰 DSH 槽位契约；"另一个界面"的体感成立 | 面板宽度窄（≤ 400px 常见），信息密度要克制 |
| B 新开一个 DSH tab | 新增 `sidebar.right.pane.tab` key（如 `dsh-elab-market`），`⚙` 调 `sidebarRightTabs.openTab(kind)` | 真正独立页面、可全屏 | `openTab` 是服务侧能力，面板组件拿不到；需在 factory 里捕获服务并注入回调，`verify-client-contract.mjs` 的假 ctx 也要同步扩展；多一份槽位生命周期 |
| C 只放在 DSH 设置页 | 扩展现有 `SettingsSection` | 零面板改动 | 与用户诉求相反（"点进设置"是从面板点，不是全局设置页）；且设置页不适合高频的安装/卸载 |

**结论：MVP 走 A。** B 作为后续可选项（当设置页内容超过单栏承载量时再拆）。

### 3.2 信息架构

```
┌─ 闭环主视图（现有） ────────────────┐        ┌─ 设置视图（新增） ─────────────────┐
│ [工程 ▾] [我点的/agent] [running] [↻][⚙] │  →   │ [← 返回]  设置 · 适配包与市场        │
│ AdaptBanner（如需）                       │        │ [ 市场 ] [ 已装 2 ] [ 内核 ]        │
│ 阶梯 + 控制条                             │        │ ┌──────────────────────────────┐ │
│ 日志尾 / 串口                             │        │ │ 搜索框           [刷新市场]   │ │
└──────────────────────────────────────────┘        │ │ 包卡片：名/版本/状态/芯片     │ │
                                                     │ │        [安装] [详情]         │ │
                                                     │ └──────────────────────────────┘ │
                                                     │ 已装页：版本/哈希/[校验][卸载]   │
                                                     │ 内核页：复用 SettingsSection     │
                                                     └──────────────────────────────────┘
```

- **入口**：`⚙` 放在工程条最右（现 `↻` 旁），图标按钮 `title="设置：适配包 / 市场"`；
  闭环运行中也可进入（只读浏览无害），但安装/卸载按钮按运行状态置灰（见 §4.6）。
- **返回**：设置视图左上 `← 返回`；切回后 `service` 快照与日志缓冲原样保留（`view` 只是本地呈现态，
  不进 `cockpit-service`）。
- **分段而非同屏**：三个页签互斥渲染，避免把"市场 + 已装 + 配置"全塞进一屏（用户明确反对）。

### 3.3 交互流程（MVP）

```
⚙ → 设置视图
  ├─ 首屏：GET /api/packs?market=0                （快：已装 + 搜索根，不联网）
  ├─ 已装页：官方源包显示「源」徽标 + [安装]       （离线安装，不依赖市场）
  ├─ 市场页：点「刷新市场」→ GET /api/packs?market=1
  │     ├─ 成功：渲染市场条目（official/community、license、requires、sha256 前 8 位）
  │     ├─ warning：顶部横幅"远程索引不可达，已用缓存/本仓索引"
  │     └─ error：空态 + 引导检查网络 / elab.host.yaml 的 packs.market
  ├─ [安装] → 二次确认（名称/版本/来源/哈希）→ POST /api/pkg/install → 进度 → 完成刷新
  ├─ [卸载] → 二次确认（不可逆）→ POST /api/pkg/remove   → 完成刷新
  └─ [校验] → POST /api/pkg/verify → 逐包 ✓/✗ + 问题列表（只读，不弹确认）
```

### 3.4 宽度三档适配

面板现按 `<420 / 420–700 / ≥700` 三档布局（`CockpitPane.tsx` 的 `usePaneWidth`）。
设置视图同样复用该宽度：

| 档 | 布局 |
|---|---|
| narrow（<420） | 单列；包卡片压缩为两行（名+版本 / 芯片+按钮）；搜索框全宽 |
| mid（420–700） | 单列但卡片一行式（名 · 版本 · 状态徽标 · 芯片 · 按钮右对齐） |
| wide（≥700） | 左列表 + 右详情（详情含 description/requires/sha256/来源/目录） |

## 4. 内核 HTTP 面补齐设计（业务层）

> 原则：**包格式、来源解析、哈希、审计、skill 重生成全部留在内核**；工具层只发请求、渲染字段。
> 与 `AGENTS.md` 规则 5/6 一致。

### 4.1 现有只读面（保持不动）

`GET /api/packs?market=0|1`（`cockpit/server.py:852-856`）→ `pkg_mod.status()`：

```jsonc
{
  "roots": ["…/packs/official", "…/packs/installed"],
  "install_root": "…/packs/installed",
  "official_root": "…/packs/official",
  "installed": [   // 含官方源目录（installed:false）
    { "name":"st/stm32", "version":"…", "vendor":"st", "platform":"stm32",
      "status":"official", "license":"…", "description":"…",
      "dir":"…", "installed":true, "sha256":"…", "chips":["st/stm32f103xb", …],
      "requires":{"kernel_api":"…","schema_version":1} }
  ],
  "chips": ["st/stm32f103xb", …],          // 仅"已安装"包贡献的芯片
  "schema_version": 1,
  "kernel_api": "…",
  "market": { "path":"…", "error":null, "warning":null,
              "packs":[{ …条目…, "installed":false }] }
}
```

### 4.2 新增写动作（建议）

| 方法 | 路径 | 语义 | 成功码 |
|---|---|---|---|
| POST | `/api/pkg/install` | 安装一个包（市场名 / 官方源 / 显式来源） | 202（异步）或 200（同步） |
| POST | `/api/pkg/remove` | 卸载已装包（只删安装目录） | 200 |
| POST | `/api/pkg/verify` | 校验（单包或全部，只读） | 200 |
| POST | `/api/pkg/update` | 按市场索引更新（单包或全部） | 202/200 |
| GET | `/api/pkg/job?job=<id>` | 异步任务状态/日志（仅异步方案需要） | 200 |

请求体（**不信任客户端提供的 sha256/source**）：

```jsonc
// install
{ "name": "artery/at32",              // 市场名（首选；内核自行查市场条目并取 sha256）
  "source": "official" }              // 可选：official=只允许 packs/official 下同名包（离线）
                                      // 缺省 = 按市场索引解析
// remove / verify / update
{ "name": "st/stm32" }                // verify/update 允许缺省 name = 全部
```

设计取舍：

- **只收 `name`，不收路径/URL/哈希**：来源解析走内核 `market_entry()` + `entry_source()`
  （`pkg.py:631-653`），sha256 取自市场条目；这样前端即使被篡改也无法把包指向任意磁盘路径。
  `source:"official"` 仅在内核 `official_root(cfg)` 下按 name 查找后走 `install(local=...)`。
- **安装后动作与 CLI 同源**：`install()` → 平台 skill 重生成 → 重建 `Config`。
  建议把 `__main__.py:668 _regen_skills()` 下沉到 `pkg.py`（例如 `install_and_regenerate()`），
  CLI 与 HTTP 共用一份实现（与 `/api/adapt` "只有一份实现"的原则一致）。

### 4.3 长任务、并发与 K1 约束

- 内核是 `ThreadingHTTPServer`（`cockpit/server.py:30,1418`），一个长请求只占一个线程，
  **不会钉死整个服务**；但工具层代理的普通请求 `fetch` **没有超时**
  （`routes.ts:218`），前端 `fetch` 也无超时——同步安装一旦卡住，UI 会"转圈到天荒地老"。
- `pkg.install()` 的耗时大头：`git clone`（`pkg.py:357-370`，**当前没有超时**）、
  archive 下载（30s 超时，`pkg.py:382`）、整树哈希（`tree_hash`）。
- **推荐：异步 job（P0 就做，代价很小）**：
  - 进程内单例 `PkgJobManager`：全局一把锁（同一时间最多一个包操作），
    `{id, action, name, state: queued|running|ok|failed, stage, log[], started_at, result, error}`；
  - `POST` 立即返回 `202 {job}`，进程内线程执行；
  - `GET /api/pkg/job?job=` 返回快照；前端 500ms 轮询，完成后再拉一次 `packs?market=0`；
  - `install()` 的 `log=` 回调直接写 job.log（阶段文案即可：校验 → 下载/复制 → 哈希 → 落盘 → skill → 重载）。
- **同步兜底**：若首版想更快，可先同步实现，但必须给 UI 明确的"安装中"态与 `AbortController`；
  后续仍建议升级为 job（与串口 `capture` 的演进路径同构：先同步后状态机）。

### 4.4 安装后的热生效（必须）

```python
# 伪代码：与 /api/adapt 写盘后的重载完全同源（server.py:1150-1157）
rec = pkg_mod.install_and_regenerate(self.cfg, name=..., log=job.log)
cfg2 = Config(self.cfg.root)
type(self).cfg = cfg2          # 原子替换
self.mgr.cfg = cfg2
```

- 在途请求仍握旧 `cfg` 跑完（旧配置对旧工程自洽），与现有注释一致。
- 卸载同理（删除后重建，让 chips 列表立即收缩）。
- 前端完成安装后应刷新：`packs`（已装列表）+ `projects`（可能出现新芯片工程）。
  建议由宿主在 `/api/pkg/*` 成功响应后不额外做缓存，前端自行重拉。

### 4.5 兼容性判定（`requires` 握手）

`status()` 已返回 `kernel_api`、`schema_version`，每个条目带 `requires`。
MVP 可以只**展示**（"要求 kernel_api ≥1 / schema v1，当前 kernel_api=x"），
由内核在安装时做**硬校验**（`validate_manifest` 已有 schema 校验；补 `requires.kernel_api` 比较）。

建议 P1 由内核在 `status()` 里加投影字段（工具层不实现语义）：

```jsonc
"compatible": { "ok": true, "reasons": [] },   // 每个 installed / market 条目
```

### 4.6 安全与运行约束

| 约束 | 处理 |
|---|---|
| 哈希强校验 | 市场安装一律用索引条目 sha256；复制后再算一次，不一致回滚（`pkg.py:476-479` 已有） |
| 来源不可信 | 不接受客户端路径/URL/sha256；仅 `name` + `source:"official"` |
| 删除保护 | `remove()` 只删 `install_root` 内目录；`force=false` 时越界拒绝（`pkg.py:527-528`） |
| 闭环互斥 | **有 run 在跑时禁止 install/remove/update**（返回 409）：包变更会换芯片/端口，跑到一半换数据最危险 |
| 串口互斥 | 不涉及；`verify` 只读可随时执行 |
| 路径/换行 | Windows 下外置包必须带 `.gitattributes`（`* -text`）；UI 校验失败时直接展示 `verify` 的 `problems` |
| 供应链 | 包内禁止可执行安装脚本（已有约束）；UI 明示 official/community 与 license |

### 4.7 错误码约定（沿用现有 JSON 错误壳）

| code | HTTP | 场景 |
|---|---|---|
| `pack-not-found` | 404 | name 不在市场/官方源 |
| `pack-already-installed` | 409 | 未带 force 的重复安装（`install()` 抛出） |
| `pack-verify-failed` | 400 | 清单/哈希/路径安全校验失败 |
| `pack-busy` | 409 | 已有包操作在跑，或闭环 run 正在跑 |
| `market-unreachable` | 200 + `warning` | 远程索引失败已回退缓存/本仓索引（不是错误） |
| `pack-op-failed` | 500 | git/IO 异常（透传原因，便于用户自救） |

## 5. 工具层改造清单（DSH 插件）

### 5.1 代理白名单（最小改动）

`src/adapters/kernel-http/routes.ts`：

```ts
GET_ALLOW  += 'packs', 'pkg/job'
POST_ALLOW += 'pkg/install', 'pkg/remove', 'pkg/verify', 'pkg/update'
```

> 代理按 `rel` 精确匹配、只允许单段/已知两段，`pkg/install` 属于允许形态；
> 不对写动作做 actor 注入（`actor` 注入仅用于 `run`），也不走 RunArbiter
> （包操作与闭环互斥由内核 409 表达，宿主不重复实现业务规则）。

### 5.2 ICD 客户端与类型

`src/adapters/kernel-http/icd-client.ts` 新增：

```ts
packs: (opts?: { market?: boolean; sessionId?: string }) =>
  request<PacksStatus>(withSession(`/elab/api/packs?market=${opts?.market === false ? 0 : 1}`, opts?.sessionId)),
pkgInstall: (opts: { name: string; source?: 'official'; sessionId?: string }) =>
  post<{ job?: string }>(withSession('/elab/api/pkg/install', opts.sessionId), { name, source: opts.source }),
pkgRemove:  (opts: { name: string; sessionId?: string }) => post(…),
pkgVerify:  (opts?: { name?: string; sessionId?: string }) => post(…),
pkgUpdate:  (opts?: { name?: string; sessionId?: string }) => post(…),
pkgJob:     (job: string, sessionId?: string) => request(withSession(`/elab/api/pkg/job?job=${job}`, sessionId)),
```

`src/domain/icd.ts` 增 `PacksStatus`、`PackInstalled`、`PackMarketEntry`、`PkgJob` 等类型，
字段与 §4.1 一一对应（**domain 只放类型，不放取值逻辑**）。

### 5.3 组件与边界门禁

两条门禁必须同时满足：

1. `test/boundary.test.mjs:32-36` 的 `CROSS_ADAPTER_ALLOWED` 是**精确白名单**：
   `adapters/dsh-web/**` 只有 `CockpitPane.tsx` 与 `SettingsSection.tsx` 可以直接 import
   `kernel-http/icd-client.ts`。
   → **新组件不要直接 import icd-client**；由 `CockpitPane` 组装 `elabApi`，
   以 props/回调下传（`api` 的类型从 domain 引入），或把取数逻辑放 `CockpitPane`。
2. `test/style-rules.test.mjs`：禁止字面色值、禁止 `--dsw-*`/`--dsh-*`、引用的
   `--elab-*` 必须在 `theme/dsw-map.ts` 有定义。

建议文件：

| 文件 | 职责 |
|---|---|
| `src/adapters/dsh-web/CockpitPane.tsx` | 加 `view` 状态、`⚙` 按钮、`← 返回`；保留 service 快照；把 `api` 传给设置视图 |

不新增槽位 → `scripts/build-client.mjs` 与 `verify-client-contract.mjs`
（其断言"注册 3 个槽位项、1 个入口卡、1 个底部工具"）**无需改动**，这是方案 A 的额外收益。

### 5.4 agent 工具（P1）

在 `src/domain/tools.ts` 增加 `elab_pkg` 契约、`src/adapters/dsh-tools/pkg-ops.ts` 实现（单工具 + `action` 枚举，风格对齐 `elab_serial`）：

```
action: status | search | install | remove | verify | update
name?:  string
```

- `status/search/verify` 只读，默认可用；
- `install/remove/update` 属于"写盘 + 联网"，必须受现有 `allowAgentWrite`
  （`main.ts` 的 `Config.allowAgentWrite`，默认 false）约束，拒绝时返回明确原因；
- 工具描述里点明"安装适配包会改变工程可用芯片，需要用户确认"。

## 6. 分层与边界合规复核

| 规则（AGENTS.md） | 本方案如何满足 |
|---|---|
| 业务代码只写业务层 | 安装/卸载/哈希/skill 重生成全部在 `services/elab/pkg.py` + `cockpit/server.py` |
| 插件只做工具层 | 插件只加白名单、客户端方法、视图组件；不解析 `pack.yaml`、不读 `market/index.json`、不 spawn git |
| 唯一缝隙是 loopback HTTP | 新组件不 import 内核源码；新增端点走既有 `/elab/api/*` 代理 |
| 内核自描述优先 | 市场/已装字段全部来自 `pkg_mod.status()`；插件不硬编码包名或厂商 |
| 芯片知识只写适配包 | 本次不改任何 `packs/**`；UI 仅展示包元数据 |
| 双检出一致 | 改 `cockpit/server.py` 后本仓与用户 elab 工作检出都要同步 |

## 8. 待决问题（需要产品侧拍板）

1. **设置视图是否也放进底部工作台版本？**
   `betterSidebar` 的底部 `registerTab` 与右栏 pane 共用 `CockpitPane`；方案 A 自动覆盖两者，
   但底部面板宽度更窄，需要确认 `narrow` 档的列表密度是否可接受。
2. **安装期间是否冻结闭环？**
   推荐"有 run 在跑就禁止包操作"（409）。反向（安装中禁止发起 run）需要宿主额外记账，
   首版可不做。
3. **是否允许 agent 自行安装包？**
   默认 `allowAgentWrite=false`（现状）；若开放，建议只允许 `status/search/verify`，
   install/remove 强制人工确认。
4. **市场首屏策略**：`market=0` 快显 + 手动"刷新市场"，还是进入即联网？
   推荐前者（离线/弱网体验稳定，且与 `load_market` 的 15s 超时解耦）。
5. **是否需要"内置包一键安装"按钮？**
   已装页会给 `installed:false` 的官方源包显示「源」徽标；若提供按钮，走 `source:"official"`
   路径（完全离线），建议保留（这是新用户最快的首次成功路径）。

## 10. 一句话回答用户

**可以加，而且不用"把全部都塞进一个界面"**：面板顶栏加 `⚙` → 整块切成设置视图
（市场 / 已装包 / 内核设置三个页签）→ `← 返回` 回闭环。
内核只差"安装/卸载/校验/更新"四个 POST 端点与安装后重载；
插件侧是白名单 + 客户端方法 + 两个展示组件，业务实现零重复。
